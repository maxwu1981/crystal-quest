# 火輪（第四级载具·飞行）+ 山顶彩蛋 设计规格

> 执行说明：本规格基于对 `~/Projects/crystal-quest` 实际代码/数据的直接读取与脚本验证（不是只看文档），所有坐标已用 Python 脚本对当前 `overworld.json` 做 BFS 可达性模拟，结果附在第 6 节。未做任何文件修改——按记忆要求，这是纯设计交付。

## 0. 决策摘要（先说结论，理由在后面对应节展开）

| 决策点 | 结论 |
|---|---|
| 山顶一格窗开几处 | **2 处**（东：`(30,3)/(31,3)` 天然孤岛；西：`(8,1)/(8,2)` 新凿），落在你给的"1–2 处"上限，也落在"2–3 处"总数下限 |
| 罗经圈呼应点 | **不做**——查过了，罗经圈是独立室内图 `cave_1`/`cave_2`（"路像罗盘一样绕"是地牢内部结构，不是 overworld 地表上的一个圈形），overworld.json 上没有任何"只有俯瞰才看得清"的既有形状可用，不勉强编。见第 6 节 |
| 山顶内容 | 东窗：1 件**新的**神话装备（不是从现有 23 件里搬一件过来——理由见第 7 节）；西窗：1 座没人拜的伯公，纯 flavor + 200 金 |
| 获得火輪的触发机制 | 新 flag `hasWheel`，由新增 NPC「唱月琴的阿伯」（`windgap_2.json`）对话 `set`，与 `summons.json` 已定义的 `summon:nezha` 同一次触发一起写入——**零新机制，复用现成的 NPC 对话 `set` 数组** |
| 起飞的解锁闸 | 起飞交互本身必须额外查 `state.flags.hasWheel`，否则任何存档开局就能在庄口草地上按确认键起飞。这是我发现的一个必须补的闸，不是原文档已经写的 |
| 新美术 | **本设计新增内容本身不需要任何新美术资产**——瓦片复用 `mountain`/`grass`，道具图标是程序生成的（`src/assets/itemIcon.js`）。唯一的美术缺口是火輪载具本身的角色精灵，那是 §6.2 已经排好的、这一级的共同前置，不是我这次新增的 |
| 发现的两个潜在 bug | ① `passable()` 的 `ride` 门禁比 `fly` 判断更早生效，竹排上线后河面会挂 `ride:'raft'`，届时火輪会飞不过河——与"海面都过得去"的既定设计矛盾，必须修；② `minimap.js` 的 `mapColor()` 按 `solid` 分色，我的一格窗 `solid:false` 但 `tile` 仍是 `mountain`，会被误画成洞窟地板灰而不是山的深灰，在小地图上露馅。两处都给了确切修法 |

## 1. 文件清单与具体改动

### 1.1 `data/maps/overworld.json`（4 处改动：legend 新增 1 项、rows 改 3 个字符、events 新增 2 个、vehicles 数组加 1 项）

**(a) legend 新增一个"火輪一格窗"字符 `r`：**

```json
"r": {
  "tile": "mountain",
  "solid": false,
  "ride": "wheel",
  "_why": "火輪一格窗（docs/交通与世界移动.md §4.3）：外观仍是山，只有骑火輪 (state.vehicle==='wheel') 能过。solid:false 是为了让 tests/cases/maps.js 的 reach() 能穿过去验证宝箱可达——reach() 只认 solid，不认 ride；真正走路的玩家会被 ride 字段挡住（见 FieldScene.passable()）。parseMap 只解构 tile/solid/encounter/counter/ride 五个字段，这个 _why 不会被读到、也不会报错，纯粹留给看 JSON 的人。"
}
```

`parseMap`（`src/field/FieldScene.js`）目前的字段解构是：
```js
cells.push({ tile: def.tile, solid: !!def.solid, encounter: !!def.encounter, counter: !!def.counter, ride: def.ride || null });
```
只取五个具名字段，`_why` 这种额外键不会进 `cells`，这是 JSON 里"写注释"的唯一办法（JSON 本身没有注释语法）。

**(b) rows 改 3 个字符**（已用脚本核对，行长度仍是 40，不会触发 `parseMap` 的行长检查）：

| 1 | 8 | `M` | `g` | 西窗降落点（复用现有 `g`=grass，走路可站） |
| 2 | 8 | `M` | `r` | 西窗本体（新 legend） |
| 3 | 29 | `M` | `r` | 东窗本体（新 legend） |

对应的整行 diff（逐字符核对过，只改了标出的那一位）：

**(d) `vehicles` 数组加一项**（这一步极易漏，务必做）：

```diff

+ "vehicles": ["oxcart", "wheel"],
```

理由：`FieldScene.loadMap` 现有逻辑是「目标图的 `vehicles` 白名单里没有当前骑的这台，就强制下车」（`src/field/FieldScene.js` 第 59 行：`if (this.game.state.vehicle && !(md.vehicles||[]).includes(this.game.state.vehicle)) this.game.state.vehicle = null;`）。overworld.json 现在只列了 `oxcart`，如果不加 `wheel`，玩家一旦从任何地方带着火輪状态"进入" overworld（比如从室内图走出来），会被立刻强制下车——整个飞行内容形同虚设。

### 1.2 `data/items.json`（新增 1 件装备，纯新增，不改任何现有条目）

```json
"qingniao_ring": {
  "name": "青鸟环",
  "type": "accessory",
  "tier": 11,
  "myth": true,
  "icon": "qingniao_ring",
  "lore": "中国神话·昆仑",
  "desc": "西王母座下青鸟遗下的环，衔来的是消息，戴着它听得见风里的话。",
  "price": 0,
  "acc": 18,
  "crit": 12
}
```

设计取舍（详细理由见第 7 节）：**这是一件全新的第 24 件神话装备，不是把现有 23 件里的某一件搬过来**。我读了 `主线设计.md` §8.3——"23 件神话装备全在第一幕会压垮曲线"是已知问题，但那一节明写"这条改动会动到 data/ 下的现有内容，本次任务不做"，且我核对过现有 23 件已经**全部**有出处（overworld 6 件、cave_3 宝箱 4 件 + boss 掉落 5 件、bogong 祭坛链 3 件、cave_1/cave_2 剩下 5 件），挪动任何一件都要同时改掉它原来的出处，牵动面比"火輪+山顶"这个任务本身大得多。新增一件是纯 additive 操作：

- `tests/cases/gear.js` 的"神话装备"测试只要求 `myth.length >= 20`（不是恰好 23），加到 24 件不会破线。
- 没有写 `cat` 字段（跟 `sampo`/`ouroboros`/`dragon_heart`/`winged_sandals` 这四件已有的饰品一样），所以豁免"必须强于同类最强材质款"那条断言（那条断言只查有 `cat` 的武器/防具）。
- 没有写 `jobs`，全职业通用，不会撞上"神话装备拿得到但全队没人能装"那条测试。
- `icon` 图标**不需要出图**——`src/assets/itemIcon.js` 的道具小图标是纯程序绘制：饰品按 `id` 正则分形状（`/ring|ouroboros/` → 戒指形，我这个 id 里带 `ring` 会自动落在戒指形状），颜色和"神话闪光"叠加层由 `myth:true` 自动套用共享的金色调色板，什么都不用另外画。
- `icons` 唯一性、`lore` 集合数量（现有已经 ≥8 种）都不受影响。

只有 1 个新增 NPC：

| 字段 | 值 |
|---|---|
| id | `yueqin_elder` |
| 位置 | `windgap_2.json` `(13,12)` |

**这个 NPC 同时做了两件事**：解锁火輪（`hasWheel`）和解锁中坛元帅召唤（`summon:nezha`，`summons.json` 里已经定义了这个 unlock 字符串，但目前全仓库没有任何地方真正 `set` 过它——我核对过 `src/`、所有 `data/maps/*.json`，八位召唤没有一个的 `unlock` flag 被实际写入过。这不是我这次任务要修的坑，但既然要做"请到中坛元帅"这个触发点，顺手把这一个的 flag 接上是免费的，不接反而会让这个 NPC 的台词和实际游戏状态对不上）。

**关于触发条件的默认决定与升级路径**（这是本设计里我做的一个"有默认值就自己拍板"的判断，写清楚给你确认）：

我**没有**把这个 NPC 的解锁变体挂在"打完應聲的 boss"上，因为 `windgap_1/2/3.json` 现在完全是程序化迷宫骨架（`"gen":{"kind":"cave",...}`），没有 boss、没有水晶事件——這部分内容根本不存在，我如果假设一个不存在的 winFlag 名字去挂钩，会产出一份实际上引用了空气的规格。

**默认方案（本规格实际采用的）**：只挂 `unless:"hasWheel"`，不设 `if` 前置条件。玩家只要走到 `windgap_2`（已经隔着 overworld→windgap_1→windgap_2 两次传送，不是从游戏一开始就摸得到的地方）跟阿伯说话就触发。这个方案今天就能直接实现，不依赖任何还没做的内容。

**推荐的后续升级（不在本次任务范围内，但留好接口）**：等"响石地牢"内容（區域 boss「應聲的」+ 水晶事件）真正落地时，参照 `cave_3.json` 的既有写法（boss NPC 的 `script.winFlag` + 水晶事件的 `needFlag` 用同一个字符串），我建议这个 winFlag 命名为 **`windgapAnswered`**（呼应"應聲的"）；到时候只需要给 `yueqin_elder` 的第一条对话变体加一个 `"if": "windgapAnswered"`，其余一个字都不用动。这是一行改动，我在此明确写出建议名字是为了让两边（我这份规格 vs 将来做响石地牢内容的人）将来对得上，不是要求现在就必须实现它。

## 4. 新增怪物/遇敌表设计

**不涉及。** 理由：

1. 火輪飞行态是 `noEnc:true`（全免遇敌），两处山顶内容都是"降落→开箱→（可选）再起飞离开"的短促流程，不需要任何守卫怪。
2. 这和现有 overworld 六个神话装备宝箱的先例完全一致——`ow_gungnir`、`ow_jade` 等六个宝箱现在也都是纯 flavor + 直接开箱，没有一个配了守卫怪。给山顶彩蛋加一场专属战斗反而是新引入的不一致。
3 . 任务原文本身把内容定位成"小彩蛋点"，不是"新迷宫/新 boss"，加怪物需要连带修 `data/enemies.json`、`data/encounters.json`，那是明显更大的一块内容，超出"火輪 + 山顶"这个任务的范围。

如果你希望山顶彩蛋更有"分量"，比起加一只新怪，我更建议维持现状（零怪物），把"分量"完全交给道具本身的稀有度（神话装备）和"只有飞上来才看得到"这件事的独特性——这是这次改动里少数几个我会主动建议"不要加"的地方。

## 6. 需要下一步验证的坐标/规则（含我已做的验证数据）

**我已经用脚本核对过、置信度高的部分**（附验证方法，供复核）：

- 用 Python 重建了 `overworld.json` 的 40×32 网格、按 legend 的 `solid` 字段跑 BFS（完全复刻 `tests/cases/maps.js` 的 `reach()` 逻辑），确认：
  - 基线（不开任何窗）：从出生点 `(20,28)` 可达 **853** 格；地图上除 6 个既有神话宝箱格外，**唯一**天然被完全封死的非 solid 格是 `(30,3)` 和 `(31,3)`（东窗那两格），别处没有"意外孤岛"。
  - 打开东窗 `(29,3)` 后：`(30,3)` 变为可达，宝箱 `(31,3)` 的"相邻可达"判定为 **True**。

## 飞行影子参数（`src/field/npc.js` 的 `drawShadow`）

现有实现（我读到的原文）：
```js
export function drawShadow(ctx, dx, dy, hgt = 1, wide = 1) {
  const cx = dx + TILE / 2 + SUN_UX * 1.5 * hgt, cy = dy + TILE - 2 + SUN_UY * 1.5 * hgt;
  const rx = TILE * 0.34 * wide, ry = TILE * 0.14;
  ...
  ctx.globalAlpha = 0.11;  // 外圈
  ...
  ctx.globalAlpha = 0.22;  // 内圈
}
```
其中 `TILE=16`，`SUN={dx:0.55,dy:1.0}` 归一化后 `SUN_UX≈0.482, SUN_UY≈0.876`。

**建议的飞行态取值**（对照"3 行就能做到"的原判断——加一个 `alphaMul` 参数，两处 `globalAlpha` 各乘一下，调用处按 `state.vehicle==='wheel'` 传不同参数）：

| 参数 | 地面态（现状） | 建议飞行态 | 换算出的像素效果 |
|---|---|---|---|
| `hgt`（复用现有参数，控制阴影沿光源方向的偏移量） | `1` | **`4`** | 偏移量从 ≈1.5px 变成 ≈6px（分量约 2.9px/5.3px），阴影明显"甩"到角色斜下方，读作"离地" |
| `wide`（复用现有参数，目前只缩放 `rx`） | `1` | **`0.55`** | `rx` 从 5.44px 缩到约 3.0px |
| **需要新加的 `ry` 缩放**（现状 `ry` 不吃 `wide`，飞行时如果只缩 `rx` 会变成一条扁线而不是整体缩小的圆点） | — | 把 `const ry = TILE*0.14` 也改成 `TILE*0.14*wide` | `ry` 同步从 2.24px 缩到约 1.23px |
| 新增 `alphaMul`（透明度整体乘数，2 处 `globalAlpha` 各乘一次） | `1` | **`0.5`** | 外圈 0.11→0.055、内圈 0.22→0.11，明显更淡 |

即：`drawShadow(ctx, dx, dy, /*hgt*/4, /*wide*/0.55, /*alphaMul*/0.5)`（骑乘火輪时的调用），落地/步行时维持 `drawShadow(ctx, dx, dy)` 不变（走默认值）。这组数字是按现有函数结构反推出的**起点值**，拿到真实精灵美术后建议再目测微调±20%（第 6 节已列为待验证项）。
