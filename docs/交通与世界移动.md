# 去屏東打怪 · 交通與世界移動

> 本档回答一件事：**这个世界怎么走。**
> 从「一张 40×32 的六堆平原、只有两条腿」，长到「七个地区、十三小时主线」之后，
> 移动本身会变成一个必须设计的系统。
>
> 前置：`docs/主线设计.md`（八幕结构、五分車已在那里定案）、`data/lore.json`。
> 本档不改任何既有设定，只往上加一层。所有地名与器物都能在 `lore.designer_checklist`
> 最后一条的清单里找到，或者是屏东真的有的东西。
>
> **本档只写方案，没有写任何代码。** 所有「改动量」都是实际数过行数的。

## 0. 先讲结论

### 0.1 阶梯（一句话表）

| 级 | 名 | 幕 | 一句话 |
|---|---|---|---|
| 0 | **两条腿** | — | 草、路、沙、林；遇敌照常 |
| 1 | **牛車** | 二（土） | 只走车辙，但车辙上不遇敌——主干道变成安全走廊 |
| 2 | **五分車** | 二末～六 | 站到站的选单传送，逐幕通车（主线设计已定案，本档只接线） |
| 3 | **竹排** | 五（水） | 溪与圳沟变成路；遇敌表换成水鬼那一套，不是变没有 |
| 4 | **火輪** | 六（風） | 山、林、海面都过得去；免遇敌；落地限可走格 |

**这不是「越后面越快」的四级，是四种不同的东西**：
牛車改**遇敌**，五分車改**距离**，竹排改**地形与敌种**，火輪改**限制本身**。
每一级解决的是不同的烦，所以拿到新的不会让旧的作废——
拿到火輪之后你还是会坐五分車，因为选单比飞过去快。

### 0.2 我建议不做的（详见第 7 节）

1. **一张巨型无缝世界地图**（把 40×32 拉成 120×96 那种）
2. **真正的昼夜循环**（改成剧情驱动的「暗晡夜」）
3. **潜水 / 海底地图**（导演明说了「在海中」，这一条是我唯一想驳回的）
4. 骑王船、载具战斗、第二套传送网、点小地图自动寻路

### 0.3 现在就能动手的第一步

**给 `legend` 加一个 `ride` 字段，给 `state` 加一个 `vehicle` 字段，先不接任何内容。**

- 改动：`parseMap` 1 行、`passable` 3 行、`state.js` 2 行（新档与旧档各一处默认值）。
- 新增：`src/field/vehicles.js`（约 50 行，一张表 + 上下车的对话流程）。
- **72 条测试原样全绿**——因为这一步没有任何一张地图用到 `ride`。
- 验证：`?debug` 下手动把 `state.vehicle` 设成 `'raft'`，再把 `overworld.json` 里
  `w` 那一条 legend 加一个 `"ride": "raft"`，就能在现有的溪上划船了。**一个 JSON 键。**

理由在 4.2：这个引擎里读 `cells[].solid` 的地方**一共只有三处**（`passable`、
`minimap.mapColor`、测试的 `reach`），所以整套载具的地基只有一个函数那么大。
先把地基铺好，牛車 / 竹排 / 火輪 就都只是往表里加一行。

## 1. 先量一件事：载具的价值不在「更快」

改任何东西之前先量。数据来自 `FieldScene.js` 与 `data/encounters.json`：

| 量 | 值 | 出处 |
|---|---|---|
| 每格移动 | 0.16 秒 | `STEP_TIME`（`FieldScene.js` 档头的常量） |
| 平原遇敌间隔 | 14–34 步，均值 24 | `encounters.plains.steps` |
| 平原上「会计步」的格子 | 858 个可走格里的 821 个（96%） | 只有 `,` / 桥 / 村 / 洞口不计 |
| 一场普通遇敌 | 目标 2–3 回合 | `CLAUDE.md` 调试段 |

于是横穿现在这张 40×32 的平原（对角约 72 格）：

```
纯走路      72 × 0.16 =  11.5 秒
遇敌        72 ÷ 24   =  3 场 × 约 20 秒 = 60 秒
合计                    约 72 秒
```

**86% 的赶路时间是战斗，不是走路。**

所以：
- 把步速从 0.16 提到 0.10（快 60%）——省下 4.6 秒。
- 把遇敌关掉——省下 60 秒。

**结论：载具第一位要改的是遇敌，速度是附送的。**
一个「只是走得快」的载具在这个引擎里几乎感觉不到；
而这也解释了为什么「牛車」这种现实里慢吞吞的东西，在这里可以是一个像样的第一级——
它慢，但是路上没事，玩家实际到达时间反而短一半。

> 顺带一条：**不要用降低遇敌率来做「更快」的错觉。**
> `主线设计` 9.5 已经立了规矩：世界退化必须是环境和台词，不是数值惩罚。
> 反过来也成立——载具带来的安宁必须是**可解释的**（牛大、车吵、小东西让路），
> 不能是「因为你升级了」。

## 2. 阶梯：从这块土地长出来

### 2.0 为什么不是马车

导演讲的是「马车」。**屏东平原没有马车。**
这里是水田与蔗田，役畜是水牛和黄牛；六堆的路是**牛車輾出来的两条沟**。
把马车放进来，第一眼就穿帮，而且穿的是这个项目最贵的那层帮
（`lore._meta.tone`：「物件与说话方式落在阿公还记得的那个年代」）。

同样地，这一级不叫「船」叫**竹排**，不叫「飞空艇」叫**火輪**——
理由在各自那一节，一句话是：**先是屏东真的有的东西，再变成载具**
（照抄 `bestiary.designer_note` 对怪物立的那条规矩）。

---

### 2.1 一级 · 牛車（第二幕 · 土）

**是什么**：庄里借的一台板車，一头水牛。你不赶车，赶车的是庄里的人；
四个人坐在车斗上，脚不沾地。

**为什么是它**：第二幕的地是**田**（`regions_beyond.土.这块地欠什么`）。
田的交通工具就是牛車。而且第二幕拔掉原石之后
「六堆平原白天也开始遇敌」——世界第一次变坏，**玩家需要一个对冲**，
否则那次退化读起来就是纯惩罚（`主线设计` 9.5 点名担心过这件事）。

**解锁什么地形**：不解锁。它反而**收窄**——只能走 `path`。

这是这一级最重要的设计决定：**第一级载具不是让你去更多地方，是让你在一条线上不被打扰。**
现在 overworld 的 55 格 `path` 正好是一条主干道：内埔庄（20,29）一路往北，
过桥（20,14–15），到罗经圈洞口（20,3）。那正是玩家会来回走十几趟的那条线。

**玩法怎么变**：

| | 步行 | 牛車 |
|---|---|---|
| 可走 | 草/路/沙/林 | **只有 `path`** |
| 步速 | 0.16 s/格 | 0.11 s/格 |
| 遇敌 | 照常计步 | **不计步**（`onStep` 里跳过那一行） |
| 上下车 | — | **「牛稠」**（路边的牛棚，定点） |

**下车之后怎么办**：牛車不是实体，是 `state.vehicle` 里的一个字符串
（为什么这么做见 7.4）。任何一座牛稠都能再上车，不存在「牛車被我停在对岸」。
第二幕先放两座（内埔庄口、竹田庄口），之后每个地区路口各一座。

**代价**：3 张角色规格的美术（见第 6 节）、`vehicles.js` 里一行表、
地图上两格换成 `cartstop`。没有新地形规则。

### 2.2 二级 · 五分車（第二幕末 → 第六幕全线）

**这一级不是我提的，`docs/主线设计.md` 3 节和 9.7 节已经定案了**，本档只做两件事：
说清楚它和其他几级怎么分工，以及它为什么不能是第一级。

**为什么不能是第一级**：**一个站不成一条线。**
第二幕开场只有内埔一座車頭，选单里只有一项，等于没有。
要到第二幕末竹田通车（两座）才有意义。前半幕的空档正是牛車的位置。
（`主线设计` 3 节写的是「幕二 · 五分車第一段通车」——本档把它精确到**幕二末**，
不是矛盾，是把「一段」定义成「两座站」。）

**分工**：

| | 五分車 | 牛車 / 竹排 / 火輪 |
|---|---|---|
| 形态 | **选单**，选站就到 | **自由移动**，一格一格走 |
| 范围 | 跨地区 | 区内 |
| 解决 | 「又要走回内埔」 | 「这张图走起来烦」/「那里去不了」 |
| 代价 | 一张站点表 + 一个选单（约 80 行，本质是 warp） | 见各节 |

**站点表**长这样（放 `data/config.json` 或新开 `data/rail.json`）：

```
[{ id:'neipu', name:'內埔', map:'overworld', x:20, y:27, flag:'rail:neipu' }, …]
```

选单只列 `flags[flag]` 为真的站。通车 = 在剧情里 `set` 那个 flag——
**现成的 NPC 对话变体就能做，零代码**（`主线设计` 7.4 已经把它列在「零代码」那一栏）。

**为什么五分車是对的**：台糖糖業鐵路真的横跨屏东平原，屏東糖廠、南州糖廠都在线上；
轨距 762mm 是标准轨的一半，所以叫「五分」。**零设定成本，全部是真的。**
而且它的年代感（甘蔗车、慢、会让人搭便车）正好落在这个游戏的调子上。

### 2.3 三级 · 竹排（第五幕 · 水）

**导演点了两级，中间这一级是我加的，而且我认为它几乎是必然的。**

理由不是「JRPG 都有船」，是这块地本身：

- `lore.places.圳沟`：庄北那条圳沟，「NPC 称它東港溪」，
  并且明写「要新增水系地名时可用：東港溪、隘寮溪、林邊溪」。
- `regions_beyond.水`：東港溪出海口、渔港、林邊魚塭、造船的寮。
- 六件鎮物里的**舊龍骨**就在河口。
- **现在这张 overworld 上已经有一条河了**：第 14–15 两行整排的水，
  只有 (20,14)(20,15) 一座桥能过；两岸第 13 行和第 16 行是沙——那是**溪埔**。
  地图早就画好了一条水路，只是现在它是一堵墙。

**是什么**：一张**竹排**（竹筏）。東港、林邊的近岸与溪上真的用这个。
不叫「船」，因为「船」在这个故事里已经被王船占掉了（见 7.3）。

**解锁什么地形**：`water`。具体是**溪、圳沟、魚塭**——内水，不是外海。

**玩法怎么变**：

| | 步行 | 竹排 |
|---|---|---|
| 可走 | 陆地 | **只有 `water`**（外加渡船頭那一格） |
| 步速 | 0.16 | 0.13（水上比走路稳，但撑篙不快） |
| 遇敌 | `plains` 表 | **`plains_river` 表**，步数 ×2 |
| 上下车 | — | **渡船頭**（`dock` 瓦片，建在岸上） |

**遇敌不是关掉，是换掉**——这一条比「水上无敌」重要得多：
水上出的是水鬼、蚵殼、招潮蟹、沉船的那一套（`主线设计` 7.3 水区清单里都有），
而 `regions_beyond.水` 的区域 Boss 就叫**討替**（水鬼讨替身）。
玩家用竹排躲开山猪，换来的是另一种东西。**便利有代价，代价是换了个对手。**

实现上这是最便宜的一条：`get zone()` 加一个后缀查找，
和 `主线设计` 7.4 #2「地图按 flag 切 encounterZone」**共用同一个改动点**。

**能到之前到不了的地方**：

1. **顺流出海口** → 東港（第五幕的地区图入口）。这是最主要的一条。
2. **逆流上溪** → 隘寮溪河床（第三幕 · 金）。第三幕本来是走路去的，
   拿到竹排之后多一条回程捷径。
3. **琉球嶼（小琉球）**——東港外海那座岛，真的靠船去。
   适合做一整块可选内容（一张岛图 + 一座庙 + 几个宝箱），
   而且它是「六堆之外」，正好接住结局字幕那句「再过去，就出了六堆」。
   > 这一条要留意：小琉球不在六堆，写的时候它应该**明显不一样**——
   > 讲的是台语不是客语，庙不一样，人对「压」这件事的态度也不一样。
   > 一个可选区域用来对照主线的世界观，比再写一个六堆庄有价值。

**下车之后怎么办**：渡船頭。同牛車，不做实体停放。
渡船頭是**建在岸上的可走瓦片**，所以走路也到得了——
**竹排永远是捷径，不是唯一通路**（这一条对测试很重要，见 4.3）。

### 2.4 四级 · 火輪（第六幕 · 風）

**导演要的「飞船」。我给的是火輪，理由是它已经在档案里了。**

`data/summons.json` 里中壇元帥的信物是「**内埔庙会阵头留下的一只小火轮**」，
而 `主线设计` 6.3 已经写死：「**火轮在庄里转不动。要到风口才转得起来。**」

也就是说：**第六幕、風口、一只会转起来的火轮**——三件事已经全部写好了，
我只是让它转起来之后多做一件事。

**是什么**：请得动中壇元帥之后，他把火輪借你们。
四个人踩着轮子离地半尺，贴着地跑，遇到山就抬起来。
**不是飞船，是「借来的脚」**——所以它是有人情的，不是机械的，
这跟这个游戏的整个词汇表（请、借、送、还）是一套的。

> 如果觉得召唤的信物与载具同源会混淆，备选是**神轎起駕**（轿自己走，人跟着跑）。
> 但我倾向火輪：它已经在数据里，而且「同一只轮子，请得动他，也载得动你」
> 是免费的一层扣合。

**解锁什么地形**：全部。山、林、海面、河、沙洲。

**玩法怎么变**：

| | 火輪 |
|---|---|
| 可走 | 一切格子（除了地图边框那一圈 `T`） |
| 步速 | 0.09 s/格 |
| 遇敌 | 全免 |
| 上/下 | 起飞：站在 `grass`/`sand`/`path` 上按 A；降落：飞行中按 A，只在可走格上降得下去 |
| 只在 | 野外图（`vehicles` 里列了它的地图）；进洞进屋自动下来 |

**能到之前到不了的地方**（这才是它的意义）：

- **山顶**。现在 148 格 `mountain` 是纯装饰的墙。开两三处顶上放东西
  （神话装备、一座没人拜的伯公、看得到大武山的一块平地）。
- **外海的沙洲**。東港溪出海口那一片，退潮才有。
- **罗经圈的正中央**。`places.罗经圈` 说「路会自己绕回原点」——
  **从上面看下去它是一个圈**，而圈心走不到。这是全作最好的一个「飞行才看得见」的画面，
  而且它把一句老设定兑现成一个地点。
- **枋寮→楓港那条海岸线**。第六幕本来就在那里。

**它不做的事**：**不做站点选单。** 那是五分車的活。
火輪是「哪里都去得了」，五分車是「不用去」。两个都留着，玩家自然会分工。

**海面 vs 海底**：火輪飞得过海面，**但不下水**。理由见 7.3。

## 3. 三个必答问题的正面回答

### 3.1 遇敌率怎么变

`FieldScene.onStep()` 现在是：

```js
const c = this.cell(this.p.x, this.p.y);
if (c?.encounter) { st.stepsUntilEncounter--; if (st.stepsUntilEncounter <= 0) this.triggerEncounter(); }
```

三种改法，**我建议第一种**：

| 做法 | 改动 | 评价 |
|---|---|---|
| **A. `onStep` 里跳过计步** | `if (c?.encounter && !V[st.vehicle]?.noEnc)` | ✔ 一行，没有 `Infinity` 进存档的问题 |
| B. `resetEncounter` 里把区间乘系数 | `rng.int(a,b)` × k | ✔ 做「减半」用这个（竹排 ×2） |
| C. 把 `stepsUntilEncounter` 设成 Infinity | — | ✘ `JSON.stringify(Infinity)` 是 `null`，违反铁律 3 |

所以最终是 A + B 各管一半：**完全免疫**用 A，**倍率**用 B。

还有一条要注意：`loadMap` 里 `if (!this.game.state.stepsUntilEncounter) this.resetEncounter();`——
**计数器是跨地图带着走的**。上下车时如果不重置，会出现「骑了一路牛車，
一下车立刻遇敌」。**建议上下车时 `resetEncounter()` 一次**（1 行）。

### 3.2 能到哪些之前到不了的地方

| 载具 | 新增可达 |
|---|---|
| 牛車 | **不新增。** 它的价值是安宁，不是可达 |
| 五分車 | 不新增（站都在走得到的地方）。它省的是时间 |
| 竹排 | 出海口 → 東港（第五幕）、上溪 → 隘寮溪（第三幕回程）、**琉球嶼**（可选区域） |
| 火輪 | 山顶（2–3 处）、外海沙洲、**罗经圈圈心**、海岸线 |

**规矩**：每一级至少要有一个「非它不可」的地点，否则它就只是数值。
但**主线绝对不可以卡在载具上**——载具是可选内容与捷径的钥匙，
不是主线的门。理由：主线卡在载具上，等于把「拔盖子」的节奏交给交通工具，
而这个故事的节奏是靠七户守的人家撑的。

### 3.3 下不下得来、在哪下、下来之后怎么办

**统一规则（三级共用，因此只写一次实现）**：

1. **载具是一个字符串，不是一个实体。** `state.vehicle` 取值 `null | 'oxcart' | 'raft' | 'wheel'`。
   地图上没有一台停着的牛車，没有一条拴着的竹排。
2. **上下车都是「面朝定点按 A」**，走现成的 `interact()` + `DialogueScene` 的 choices。
   **手机上不需要任何新按钮**——这一条是硬约束（`src/touch.js` 现在只有
   十字键 + A/B + 图/音两个小钮，再加就挤了）。
3. **火輪例外**：降落不需要定点，飞行中按 A，脚下是可走格就下来。
4. **换图自动下车**：地图 JSON 加一个 `vehicles: ['oxcart','raft']`（缺省 = 空）。
   `loadMap` 里一行：目标图不许这台载具就 `state.vehicle = null`。
   否则玩家会骑着牛車走进客栈。
5. **下来之后**：站在原地，什么都不会丢。回到任何一座牛稠 / 渡船頭都能再上。

> 这一条（不做实体停放）是我最坚持的一个决定，理由写在 7.4。

## 4. 地图与地形要动什么（最小改动方案）

### 4.1 现在的可走判定是什么

**只有一条**：

```js
// FieldScene.passable —— 全档唯一的可走判定
passable(x, y) { const c = this.cell(x, y); return !!c && !c.solid; }
```

`solid` 从 `legend` 来（`parseMap` 里逐格 push 的那一行），
外面再包一层 `walkable()` 处理 NPC、宝箱、事件格。

**整个 `src/` 里读 `cells[].solid` 的地方一共两处**：上面那一行，
和 `minimap.js` 的 `mapColor`。（测试里另有 4 处，见 4.3。）
`terrain.js` 一个字都没读——它全部按 **tile 名字**判断
（`FRINGE` / `CASTER` / `WETTABLE` / `MIRROR` / `NO_TOUCH` / `SEAMABLE`）。

**所以：改可走判定不会碰到地形渲染层。** 这是这套方案能这么便宜的根本原因。

### 4.2 最小改动方案

**新增一个 legend 字段 `ride`，值是载具 id。**

```
"w": { "tile": "water", "solid": true, "ride": "raft" }
```

语义：**这一格只有骑着 `raft` 的人过得去，`solid` 对它不作数。**

```js
// parseMap（+1 个键）
cells.push({ tile: def.tile, solid: !!def.solid, encounter: !!def.encounter,
             counter: !!def.counter, ride: def.ride || null });

// passable（3 行）
passable(x, y) {
  const c = this.cell(x, y); if (!c) return false;
  if (c.ride) return c.ride === this.game.state.vehicle;   // 载具专用格：solid 不管
  const v = VEHICLES[this.game.state.vehicle];
  return v ? (v.fly || v.only.includes(c.tile)) : !c.solid;
}
```

配套的另外五处，各 1–2 行：

| 位置 | 改什么 |
|---|---|
| `FieldScene` `STEP_TIME` | 常量改成读 `VEHICLES[vehicle]?.step ?? 0.16` |
| `FieldScene.onStep` | 计步那一行加 `&& !V[vehicle]?.noEnc` |
| `FieldScene.get zone` | 加载具后缀查找（`plains` → `plains_river`） |
| `FieldScene.loadMap` | 目标图不许这台载具就卸下 |
| `FieldScene.render` | 骑着的时候画载具精灵、不画装备叠加层 |
| `FieldScene.walkable` | NPC 一律不许踩 `ride` 格（1 行） |
| `minimap.mapColor` | `ride` 格另给一色（不然河会被画成「洞窟地面灰」） |
| `state.js` | 新档 `vehicle: null`；`loadGame` 里 `st.vehicle ??= null`（旧存档兼容） |

**新档 `src/field/vehicles.js`（约 50 行）**：一张表 + 上下车的对话流程。

```
oxcart: { name:'牛車', only:['path','cartstop'], step:0.11, noEnc:true,  board:'cartstop' }
raft:   { name:'竹排', only:['water','dock'],    step:0.13, encMul:2, zone:'river', board:'dock' }
wheel:  { name:'火輪', fly:true,                 step:0.09, noEnc:true,  board:null }
```

> **上下车的对话流程一定要写在 `vehicles.js`，不要写进 `FieldScene`。**
> `FieldScene.js` 上限 400 行，写这份档时是 344 行，而另一条线正在同时改它——
> 量的时候已经涨到 358。上面那八处再加约 +15 行就压到 373，余量只剩二十几行，
> 再塞一段对话流程必破线。这不是洁癖——`CLAUDE.md` 记着两次「拆文件之后
> 测试全绿但游戏是坏的」，破线之后被迫拆分才是真正的风险。

**overworld 现在要改的，只有一个 JSON 键**：

```diff
- "w": { "tile": "water", "solid": true }
+ "w": { "tile": "water", "solid": true, "ride": "raft" }
```

没有新瓦片、没有新地形规则、没有重画地图，河就能划了。

### 4.3 和那 72 条测试怎么共存（这一节最重要）

`tests/cases/maps.js` 的 `reach()` 只认 `solid`：

```js
if (c.solid || chests.has(k)) continue;
```

它**不知道有载具**。于是有两种写法，各有代价：

| 写法 | `reach()` 看到的 | 好处 | 代价 |
|---|---|---|---|
| **A. `solid:true` + `ride`** | 墙 | 可达性断言**保持原有强度** | 那一格背后不能放 warp / chest / NPC，否则测试红 |
| **B. `solid:false` + `ride`** | 可走 | 船能带你去只有船到得了的地方 | 可达性从「走得到」降级成「**有全部载具就到得到**」 |

**我的方案：A 打底，B 只开一格。**

> **「一格窗」规则**：`ride` 格默认写 `solid: true`。
> 只有当那一格背后确实有**非它不可**的内容时，才把**通往它的那一格**
> 改成 `solid: false` + `ride`，并且在地图 JSON 里写一句为什么。
> **每放松一格都是一次记账。**

这样 `reach()` 在全图仍然是严格的，只在那几个刻意开的口子上被放松一格。
而 BFS 越过那一格之后立刻又撞上 `solid:true` 的水，**不会漏进整条河**。

具体到现在这张 overworld，一格窗只需要开在河道的两端：

- **(1,14)** ——西端，出海口方向。邻格 (1,13) 是沙、走得到，所以 BFS 到得了它；
  它的另外三个邻居 (2,14)(1,15)(0,14) 全是 solid，BFS 到此为止。
- **(38,14)** ——东端，上溪方向。同理。

这两格上各放一个通往邻区地图的 warp。**放松总量 = 2 格 / 1280 格。**

火輪同理：每一处「只有飞得到」的地方，在它和外界之间开**一格**
`{ solid:false, ride:'wheel' }` 的风口；降落台本身写成普通的可走格
（`grass`/`sand`），否则玩家一落地就站在自己过不去的格子里。

**还要顺手确认的三条**：

- `地图联通`（`tests/cases/maps.js`）按 **warp 图** BFS，且断言
  `seen.size === Object.keys(data.maps).length`——**每一张新图都必须挂在 warp 图上**。
  竹排能到的岛也一样：岛上要有一个 warp（哪怕只是通往岛上的庙），
  或者干脆把岛做成 overworld 的一部分。
- `NPC 站在可走格` 只查 `!c.solid`：**不要把 NPC 放在一格窗上**（会过但意义不对）。
- 新增 `dock` / `cartstop` / `rail` / `station` 四个瓦片之后，
  跑一次 `python3 tools/chestfit.py`，并检查它们要不要进
  `terrain.js` 的 `NO_TOUCH`（`dock` 和 `station` 要，跟 `bridge` 同类）。

### 4.4 新瓦片的完整清单（每个都要走五步）

加一个瓦片不是加一张图。每一个都要：

1. `assets/art/master/tile_<id>.png`（128×128 母版）→ `tools/set_art.py 6` 派生
2. `src/assets/tiles.js` 里一个程序化 fallback（项目坚持保留 fallback）
3. `src/assets/terrain.js`：要不要进 `FRINGE` / `NO_TOUCH` / `WETTABLE` / `MIRROR` / `DECO`
4. `src/field/minimap.js` 的 `mapColor` 加一色
5. `data/maps/*.json` 的 legend 里用它

本档要的新瓦片一共 **4 个**：`dock`（渡船頭）、`cartstop`（牛稠）、
`rail`（五分車轨）、`station`（車頭月台）。
`water` / `path` / `sand` / `bridge` / `plank` 全部复用现成的。

## 5. 世界地图要不要变大

### 5.1 现在这张够不够

不够。数据：

| | 现在 |
|---|---|
| overworld | 40×32 = 1280 格，可走 858 格（67%） |
| 屏幕能看到 | 16×14 格 → 全图是 2.5 屏宽 × 2.3 屏高 |
| 横穿一次 | 约 72 秒（见第 1 节） |
| 承载 | 一个地区（后堆内埔 + 罗经圈 + 大武山山脚） |

`主线设计` 要七个地区、每区 8–11 张图，其中 **1–2 张野外图**。
所以最终会有 **7–9 张野外图**。

### 5.2 但**不要**把单张拉大

**这是我三条「不做」里的第一条**，理由全部是量出来的：

| 限制 | 数字 | 出处 |
|---|---|---|
| 小地图会退化 | 超过 54 格宽就固定 scale=1 | `renderMinimap` 的 `MAX = 54` |
| 小地图会吃屏幕 | 40×32 已占屏幕 15.6%×14.3%；**80×64 会占 31%×29%** | 256×224 逻辑分辨率 |
| 全图硬上限 | scale=1 时 **216×168**，可读上限约 120×96 | `renderFullMap` 的 scale 算式 |
| 烘焙成本 | `buildTerrainFx` 是 O(w×h×8)，120×96 是现在的 **9 倍** | `buildTerrainFx` 的双层循环 |
| 手写风险 | `parseMap` 行长不一致直接 throw；120 字的行手写必错 | `parseMap` 的行长检查 |

**小地图那一条是硬伤**：这个游戏要能在手机横屏用触控玩
（`docs/手机上玩.md`），而横屏时右上角本来就是拇指够不到、
又最需要留白的地方。一张 80×64 的世界地图会让小地图盖掉三分之一个画面。

拉大单图要付的代价是：重做小地图（做成跟随镜头的窗口）、
重做全图（做成可滚动/可缩放）、承受换图时的烘焙停顿。
**换来的只有「没有接缝」。这笔不划算。**

### 5.3 建议：一个地区一张 40×32，用「路口 warp」相接

- **尺寸**：40×32（照现有的），最多放宽到 48×40。上限的理由是小地图。
- **数量**：7–9 张。
- **接法**：边缘一列/一行做 warp，落点在对面那张图的**第 2 格**
  （不能落在 warp 上——`tests/cases/maps.js` 的「传送目标落在另一个传送点上」卡着这一条）。
- **联通**：`地图联通` 测试本来就按 warp 图 BFS，多图天然合规。
- **五分車 / 竹排 / 火輪 全部落在同一个原语上**：warp。所以不是三套东西。

**「现在只有 warp 一种手段」够不够？够。** 但建议给它加一个字段：

```
{ type:'warp', kind:'edge', to:{...} }
```

现在所有 warp 都 `audio.sfx('door')` + 淡出（`onStep` 里 warp 那一支）。
**从平原走到河床听见开门声是错的。** `kind:'edge'` 换个音效（脚步 / 风）、
淡入淡出快一档就够。约 5 行，纯体感。

### 5.4 顺带：一张「屏東全境」示意图

五分車选单需要一张底图。建议做**一张不可走的示意图**
（约 96×64，纯 PNG，不进 `parseMap`、不参与任何测试），
上面标出通了车的站。

代价：一张美术。收益：这是玩家**唯一一次看见整个屏东**的机会，
而「世界很大」这件事，一张示意图比八张能走的地图更有效。

## 6. 载具在画面上长什么样

### 6.1 精灵怎么处理

现在的画法（`FieldScene.render` 里挑精灵那几行）：

```js
const spr  = this.game.sprites[`${leader.jobId}_${p.dir}_${frame}`];
const gear = layersFor(leader, p.dir);              // 穿在身上的装备
```

**建议：骑上去之后整个换掉，不做「人 + 载具」两层。**

```js
const rid  = this.game.state.vehicle;
const spr  = this.game.sprites[`${rid || leader.jobId}_${p.dir}_${frame}`];
const gear = rid ? [] : layersFor(leader, p.dir);
```

理由：
- **走的是现成的角色管线**，`char_<id>_<view>[_walk].png`，一个字都不用改
  （`src/assets/art.js` 的 `loadArt` 按 `characters` 那一段读，
  `right` 由 `left` 镜像，缺迈步帧自动退回程序化下沉）。
- 不做两层的原因是**组合爆炸**：6 个职业 × 3 台载具 × 3 视角 = 54 张，
  而且装备叠加层（`equip.js`）是按人画的，骑在牛車上完全对不上。
  载具精灵里自带一个笼统的乘客就够——**这是 16px 游戏的标准做法**。

**尺寸一律按角色规格出（逻辑 16×24，母版 128×192）。**
`drawArt` 从左上角画、按 `artH(spr) - TILE` 把脚对齐格子底
（`render` 里 `artH(spr) - TILE` 那一句），所以**高**可以超格，**宽**超格会往右溢出。
第一版把牛車侧面画进 16 逻辑像素宽（挤，但这是这个游戏的分辨率）。
以后要 32 宽，只需在那一行加半格居中偏移——1 行，先不做。

**影子**：`drawShadow` 现在贴脚下（`npc.js`）。
火輪飞行时影子要往下挪、缩小、加一点透明——3 行，值得做，
因为**离地感全靠影子**，没有影子的飞行看起来是「贴在地上滑」。

### 6.2 要新增的美术清单

按 `assets/art/master/` 的母版规格出图（角色 128×192、瓦片 128×128），
出完跑 `python3 tools/set_art.py 6`。

**角色规格（`char_*`，128×192）——18 张**

| 档名 | 说明 |
|---|---|
| `char_oxcart_down / up / left`（+ `_walk`） | 牛車。正面是牛头朝你、侧面最难画（车斗要压缩进 16 格宽） |
| `char_raft_down / up / left`（+ `_walk`） | 竹排。`_walk` 帧＝撑篙的那一下 |
| `char_wheel_down / up / left`（+ `_walk`） | 火輪。`_walk` 帧＝轮子转半圈 + 人略起伏 |

> `up` 视角（背面）三台都最省事，因为看不见脸。
> `left` 镜像出 `right`，所以侧面只画一张——**但牛車侧面镜像之后牛会朝反方向**，
> 这是唯一一处要人眼确认的。

**瓦片（`tile_*`，128×128）——4 张**

| 档名 | 说明 |
|---|---|
| `tile_dock` | 渡船頭。木栈探进水里，一根系缆的柱 |
| `tile_cartstop` | 牛稠。路边的棚 + 车辙分岔 |
| `tile_rail` | 五分車轨。两条窄轨 + 枕木，草从缝里长出来 |
| `tile_station` | 車頭。矮月台 + 一块站牌 |

**战斗背景（`bg_*`，不派生、直接用母版）——1 张**

| 档名 | 说明 |
|---|---|
| `bg_river` | 水上遇敌的背景（水面 + 远处的溪埔与竹丛）。`plains_river` 遇敌表要用 |

**其他**

- 五分車选单的「屏東全境」示意图 1 张（5.4，可选）
- 载具不需要道具图标——它们不进背包，不进 `items.json`

**合计：18 张角色 + 4 张瓦片 + 1 张背景 + 1 张示意图 = 24 张。**
参照现有 78 张的规模，这是一次中等批量。

## 7. 除了载具，还有什么让世界变大的手段

**每一条都写清楚：解决什么问题、代价多少、做还是不做。**

### 7.1 建议做

| # | 手段 | 解决什么 | 代价 | 备注 |
|---|---|---|---|---|
| 1 | **五分車站点网** | 跨地区来回跑（`主线设计` 9.7 估计不做会吃掉 3 小时） | 站点表 + 选单，约 80 行；通车全靠对话变体 `set` flag，零代码 | 已定案 |
| 2 | **伯公「借路」** | 迷宫深处走回头路 | **一件 `field:true` 的消耗品 + 一个 warp，约 20 行** | 见下 |
| 3 | **可修的捷径 / 流籠** | 「第二次经过同一段路」 | **零代码**：用 NPC/warp，不改 `parseMap` | 见下 |
| 4 | **单向的下山路** | 第四幕（木）→ 第五幕（水）之间的赶路 | 一个单向 warp + 一段演出 | 见下 |
| 5 | **地形机关**（涨潮淹路 / 落山風推人 / 罗经圈绕回原点） | 不加地图也能让同一张图走出不同的路 | 见下 | |

**2 · 伯公「借路」**
六堆「田头田尾都是伯公」（`lore.language.hakka` 明列），是最日常的神。
做成一件消耗品：用了之后回到**最近一座伯公坛**。
说明文字应该是这个游戏的语气：「跟伯公讲一声。他会送你到路口。」

> **注意：这是我用来替掉「第二套传送网」的东西。**
> 我一度想做「拜过的伯公坛之间互相传送」，那会和五分車功能重叠。
> **一个点对点网络就够。** 伯公降级成单向回程，两者互补而不打架。

**3 · 可修的捷径**
一座断掉的便桥、一段塌了的隘寮路、一道关起来就能走过去的圳沟水閘。
修好之后永久开着，**下一次经过就少绕十几格**。

实现上有个陷阱要避开：**不要做「flag 改变某一格的 solid」**。
`parseMap` 现在是静态的，加 flag 条件之后测试里的 `parseMap` 拿不到 flag，
可达性断言会开始说不清自己在测什么。
**用现成的 warp 就好**：一个「渡船頭的阿伯」，收你五箍送你过溪，
修好桥之后他换成一句「不用了，桥好了」，桥那一格是一个普通的 warp。
**零代码，纯 JSON，而且比机关更有人味。**

**流籠**（拉着钢索过溪的吊篮）也归这一类。台湾山区真的有，
而且它的形状正是「一个点到另一个点」——不是载具，是一格 warp。
第四幕的山脚林区最适合放一条。

**4 · 单向的下山路（木馬道滑降）**
`主线设计` 第四幕的迷宫就是**腦寮与木馬道**——木馬道是拖木头下山的木轨。
坐上去滑一趟下山，是真的（樟腦與木材就是这么下来的），
而且它把第四幕的工业遗迹变成一条捷径。**单向**：上山还是要走，
这一条不要做成往返——「木頭下得来，人上不去」本身就是那一幕的味道。

**5 · 地形机关**（这一条是「不加地图就让世界变大」的最便宜的办法）

- **涨潮淹路**（`regions_beyond.水` 已经写了「林邊魚塭下陷区，涨潮会淹路」）。
  实现建议：**做两张图 `linbian_low` / `linbian_high`，不做一张图两个状态。**
  两张图各自独立通过可达性与联通测试，零引擎改动。
- **落山風推人**（第六幕）：某些格子会把你往南推一格，像冰面。
  `onStep` 里一个格子属性，约 10 行，只在风口那张图用。
- **罗经圈绕回原点**（`places.罗经圈` 的老设定）：走到某几格就传回入口。
  现成的 warp 就能做，**零代码**，而且它把一句三百年的规矩变成一个机制。

### 7.2 建议**不做**

| # | 手段 | 为什么不做 |
|---|---|---|
| 1 | **一张巨型无缝世界地图** | 数据见 5.2。小地图在手机横屏上会盖掉三分之一画面；全图硬上限 216×168；烘焙成本 9 倍。换来的只有「没有接缝」 |
| 2 | **真正的昼夜循环** | 见 7.3 |
| 3 | **潜水 / 海底地图** | 见 7.3 |
| 4 | **骑王船** | 见 7.3 |
| 5 | **第二套点对点传送网**（伯公坛互传） | 和五分車功能重叠。玩家不会用两个选单。降级成单向回程（7.1 #2） |
| 6 | **载具战斗 / 骑乘进战斗** | 战斗系统是四人固定阵；加一个「载具行动」等于开第二套战斗规则。而 `CLAUDE.md` 已经立过一次同样的规矩：「MP 是唯一的资源，不要再加第二套货币」 |
| 7 | **点小地图自动寻路** | 和步数遇敌天生打架（自动走一半被打断，回来还要重新点）。触控已经有十字键，这一条解决的问题不够大 |
| 8 | **载具耐久 / 燃料 / 过路费** | 同 #6：第二套资源。过路费做成一次性的剧情桥段可以，做成系统不行 |

### 7.3 三条要展开讲的「不做」

**① 真正的昼夜循环**

诱惑很大，因为 lore 已经写好了：
`places.六堆平原.encounter_flavor`「白天是山猪跟虎头蜂，**暗时才轮到魔神仔跟水鬼**」。

**但成本不在引擎，在文本。**
色调层是现成的（`ambience.js` 的 `MOOD` 已经是一层 multiply，插值几乎免费），
遇敌表切换的钩子和 `主线设计` 7.4 #2 共用。**真正的代价是 NPC。**

`主线设计` 7.1 算过：完成后 184 个 NPC，每个按规矩要写 3 个变体
（任务前 / 进行中 / 拔掉之后），已经是 450 段对话，
而 0.2 节明写「这个项目的瓶颈从来不是数量，是每一行的质量」。
**再乘一个昼夜就是 900 段**，而且一个庄的人晚上该在哪、在做什么，
每一个都要重新想。这会直接压垮 `designer_checklist` 的质量线。

**替代方案：做「剧情驱动的暗晡夜」。**
某些幕、某些图**就是**夜里的（`MOOD` 里一条 tint、`encounterZone` 里一个 `_night` 表）。
玩家一样看得到夜、一样打得到魔神仔，而**每张图只有一个时间**，
NPC 变体数量一个不加。**收益的九成，成本的一成。**

**② 潜水 / 海底**

导演明说了「可以在海中进行」。这是我唯一想正面驳回的一条。

- **成本**：一整套新瓦片（海床、珊瑚、沉船、水草）、新的可走判定层、
  新遇敌表、新战斗背景、至少一张迷宫。按第 6 节的规格是 20+ 张美术。
- **收益**：这个故事的水在 `regions_beyond.水` 里是**河口、魚塭、下陷的地**，
  欠的是「抽地下水 → 地层下陷 → 海水倒灌」。**它的水是浅的、是脏的、是人搞出来的。**
  海底奇观和这一笔债没有关系。
- **而且**：`lore._meta.tone` 第一条是「先写日子，再写怪」。
  海底是这个世界里唯一一处**没有日子**的地方——没有人在那里过生活，
  也就没有人可以让玩家问「可不可以停」。

**替代方案**：火輪飞过海面就够。要「水下」的内容，
放**退潮才露出来的沙洲**和**沉船的**（`主线设计` 7.3 水区清单里已经有「沉船的」这只怪）。
那两样在这个故事里是有账的，海底没有。

**③ 骑王船**

王船是第五幕的鎮物（**舊龍骨**）所在，也是全作主题的转轴：
`regions_beyond.水.揭示` 写着「東港烧王船就是**送**：不是压住瘟疫，
是造一艘船，请上去，好好送出海」。

**「送」是这个游戏对「压」的唯一答案。** 把它变成交通工具会一次毁掉两件事：
玩家对王船的敬畏，和秀琴那条线的落点。

竹排存在的一半理由就是**替王船挡住这个诱惑**——
它是同一片水上一个平常、够用、没有神圣性的东西。


### 7.4 为什么载具一律不做「实体停放」

前面 2.1 与 3.3 都提到「载具是一个字符串，不是一个实体」。理由值得单独讲，
因为这是整套方案里**省下最多东西的一个决定**。

**如果做成实体**（地图上有一台停着的牛車、一条拴着的竹排），你要多做四件事：

1. `state` 里多一份 `{ map, x, y }`——每台一份，还要进存档，还要兼容旧档。
2. 渲染层多一类「地图上的物件」：现在 `render` 只画瓦片、事件、NPC 和主角，
   要再插一类，还要参与 y 排序。
3. `walkable` 要把它当障碍（不然人会站进船里）。
4. **一个新的失败状态：船停在对岸。**
   这是这类系统里最经典、也最没有价值的挫败——玩家没有学到任何东西，只是走了一趟回头路。

**如果做成状态**（`state.vehicle` 是 `null | 'oxcart' | 'raft' | 'wheel'`），
上面四件全部消失，代价只有一句设定：**上下车只在定点**（牛稠 / 渡船頭）。

而这句设定本身是对的——**渡船頭本来就是「船在的地方」**。
真实世界里你也不会把渡船划到半路上跳下来。
所以这不是为了省工偷来的简化，它就是这件事本来的样子。

> 例外只有火輪：它可以在任意可走格降落。理由是它不是船也不是车，是借来的脚——
> 脚落在哪里都行。而它降落之后 `state.vehicle` 变回 `null`，一样不留实体。

## 8. 施工顺序

分四步，每一步都能停下来、都能通过全部测试。

**第 0 步 · 地基（半天）**
`ride` 字段 + `state.vehicle` + `src/field/vehicles.js` 的空表。
不接任何内容，72 条测试原样绿。用 `?debug` 手动设 `state.vehicle` 验证。

**第 1 步 · 牛車（一天）**
它最便宜：不加新地形规则、只加一个 `cartstop` 瓦片、
主干道 `path` 现成。同时把「遇敌跳过计步」和「换图自动下车」两条验通。
**这一步做完，第二幕的世界退化就有对冲了。**

**第 2 步 · 五分車（一天）**
站点表 + 选单。它和第 1 步没有依赖，谁先都行，
但它跨地区，所以要等第二张野外图（隘寮溪河床或竹田）落地才看得出价值。

**第 3 步 · 竹排（两天）**
`dock` 瓦片、`plains_river` 遇敌表、`bg_river`、
overworld 那一个 JSON 键、两格一格窗、以及第一张水路能到的新图。
**做到这里就该停下来通玩一次**，问一个问题：
*上了竹排那一刻，玩家感觉到的是「我拿到载具了」还是「这条溪本来就在那里」？*
如果是前者，说明竹排给早了或者给得太顺——它应该是从东港那户造船的人家手里来的。

**第 4 步 · 火輪（两天）**
飞行规则、降落规则、影子、几处一格窗、山顶与圈心的内容。
这一步排最后不是因为它难，是因为**它会把前面几级的价值吃掉一部分**——
必须先确认牛車和竹排各自站得住，再放这个进来。

## 9. 风险

**① 载具会让「世界在变坏」这件事失效。**
`主线设计` 的核心是「进度就是破坏」：每拔一颗鎮物那块地就更差。
而载具的方向正好相反——玩家越往后越舒服。
**处理**：让每一级载具都在**同一幕**拿到那次退化的补偿，
而且台词要点破这层交易。牛車那句应该是庄里人讲的：
「田路这阵不好行了，你们坐车去。」——**载具是变坏的证据，不是奖励。**

**② 竹排会让第三幕变得可以跳过。**
逆流上溪能到隘寮溪河床，等于给了第三幕一条后门。
**处理**：竹排在第五幕才拿到，那时第三幕早过了。逆流只是**回程**捷径。
如果以后要调整顺序，这一条要重新看。

**③ 火輪会让五分車变成废物。**
**处理**：五分車是选单（瞬间），火輪是走路（快，但要走）。
只要两张地图之间的距离够远，选单永远赢。**不要给火輪任何选单。**

**④ 手机上多一层「我现在骑着什么」的状态。**
横屏上没有地方放状态指示。
**处理**：骑着的时候精灵本身就是载具，这就是指示器。
不要加 HUD。上下车都在定点、都走 A 键，玩家不会迷失。

**⑤ `FieldScene.js` 会破 400 行。**
写这份档时 344 行，量的时候已被另一条线改到 358；本档的改动约 +15 行，落在 373 上下，
余量只剩二十几行。
**处理**：上下车流程、载具表、飞行降落判定**一律写在 `vehicles.js`**。
真的要拆的话，缝应该切在「移动与碰撞」和「事件与对话」之间，
拆完必须跑 `python3 tools/lint_modules.py`（这个坑项目栽过两次，两次测试都全绿）。
