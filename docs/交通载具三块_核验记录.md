## 1. 【已推翻】不要照做的两条

### 1.1 「`furnace_1`/`furnace_2`（炉底）在真实游玩里走不到，6 件秘银装备是死内容」——**不成立**

火輪那份的「额外发现」。我从 `village.json` 出 overworld 的实际落点 `(20,28)` 起跑 BFS
（只走非 solid 格、踩到 warp 格即算用掉出口不再扩展），**11 个 warp 出口全部步行可达**，
`furnace_1(3,3)` 与 `fort_ailiao(2,6)` 都在内。西北角不是死袋：`x=1..5` 有一条连续草地
走廊从 `y=4` 一路通到 `y=12` 接上全图（把 `rows` 的 `x=0..12,y=0..12` 印出来一眼就看得到）。

它的 BFS 模型有问题（推测是把 `F`/`forest` 当成 solid，或起点取错）。
**教训**：这条正是它拿来当主要证据的那套 BFS——工具错了，用同一套工具得到的**所有**空间结论
都要打问号，不只是这一条。

### 1.2 「summons.json 的 unlock 旗标全库没人 set，义民爷永远请不到」——**不成立**（这条是我自己先误报的）

9 尊召唤都写了 `unlock: "summon:*"`，全库确实没有任何地方 set 这些旗标。但
`src/game/jobskill.js:170` 写明「只管职业等级这一道闸；剧情 flag（summons.json 的 unlock）
那一道**由调用方另外查**」，而 `src/` 里没有任何调用方查它——所以请神**只按职业等级解锁**，
九尊都请得到。

**真正成立的是弱化版**：那组剧情旗标目前是**声明了但没接线**的死字段。数据层说义民爷来自
「第二幕 竹田忠義祠」，代码层按职业等级白送。这不是 bug，但是个说一套做一套的坑，
以后真要做剧情闸时要先知道现在没有闸。

## 2. 硬冲突（三份之间，必须先解才能两份并存）

### 2.1 【已核】`overworld.json` legend `"r"` 双重定义

竹排＝`{tile:water, ride:raft}`（一格窗在 `(1,14)`）；火輪＝`{tile:mountain, ride:wheel}`
（一格窗在 `(8,2)`/`(29,3)`）。JSON 重复键取最后一个，**谁后落地谁静默重定义对方的格子，
而 96 条测试照样全绿**（两者都 `solid:false`，可达性 BFS 照样穿得过）。

**解**：`overworld.json` 现在只用掉 12 个 legend 字元（`, E F K M S T V b g p w`），
英数字元还空着 51 个，代价为零。定一条**惯例**免得下一级再撞：
**一格窗的字元＝它伪装的地形的英文首字母小写** → `r`=raft（水）、`m`=wheel（山）。
（`m` 未被占用；大写 `M` 是 mountain，小写 `m` 空着，视觉上还刚好呼应。）

### 2.2 【已核】`overworld.json` 顶层 `vehicles` 数组被两份整行覆写

现况是 `["oxcart"]` 单元素。竹排写 `["oxcart","raft"]`、火輪写 `["oxcart","wheel"]`，
两份都是整行取代。**谁后落地谁把对方的载具删掉**，`loadMap` 进 overworld 就强制下车，
那一整级形同虚设。**没有任何测试看这个字段。**

**解**：一次写成 `["oxcart","raft","wheel"]`，不要分两次改。

### 2.3 【已核】`FieldScene.js` 的 400 行铁律

实测现况 **385 行**，余量 15 行。三份各自算自己的余量（五分車写「落在 387，余量还剩 13 行
——安全」，这句只在它单独落地时成立），叠起来约 397，而火輪还有一整块没编列的起飞/降落代码。

**解（这条同时解掉一半的架构问题）**：新逻辑**全部放进 `src/field/vehicles.js`**，
不要碰 `FieldScene.js`。那个文件现在只有 **32 行**，余量 368 行，而且它本来就是载具的家：
一张 `VEHICLES` 表（`only` / `fly` / `step` / `noEnc` / `board`）＋ 一个 `tryBoard()`。
`FieldScene.js` 那边理想改动 = 0 行。

顺带作废五分車那份要新建的 `src/field/rail.js`：五分車是「两个站点之间的定点传送选单」，
和竹排/火輪的「换一个字符串、改能走的格子」是同一套机制的两种参数，没有理由另起一个模块。

### 2.4 【agent】`minimap.js` 的 `mapColor()` 第一行被两份重写，而且理念相反

火輪要让一格窗在小地图上**看不出来**（不剧透），竹排要把可划水道画成**亮蓝**（好找）。
套在竹排实际只开一格的情况上，就是深色河道中央一颗发亮的剧透蓝点。

**解**：跟火輪走（一格窗不特殊着色）。竹排「好找」的需求靠 NPC 对话给线索，不靠小地图。

### 2.5 【agent】`passable()` 的 `fly`/`ride` 判定顺序

火輪要改的是竹排依赖的函数。**顺带更正一条**：火輪把「竹排上线后火輪飞不过河」列为最高
优先级风险，但前提不成立——竹排实际没给 `w` 加 `ride`，真正被挡的只有 `(1,14)` 那一格。

## 3. 【已核】载具机制本身的四个真 bug（不是规格的错，是现有代码的洞）

这四条是三份规格共同踩到的地基问题，**必须先修，否则三份都做不成**：

| # | 现况 | 后果 | 修法 |
|---|---|---|---|
| 1 | `overworld.json` 的 `w`（水）是 `{tile:water, solid:true}`，**没有 `encounter`**；全图只有 `g`/`p`/`F`/`S` 有 | `FieldScene.js:186` 只在 `c?.encounter` 时走遇敌倒数 → **竹排在水上永远遇不到怪**，整段水域遇敌设计＋新怪 `shipwreck` 是死内容 | `w` 加 `"encounter": true` |
| 2 | `passable()`（`FieldScene.js:116-121`）骑乘时 `v.only.includes(c.tile)`，**完全不看 `solid`** | 竹排 `only:['water']` 会开放**整条河**，不是规格说的一格窗。且河被 `(20,14)/(20,15)` 的桥切成东西两段，**没有任何 `dock` ＝ 上了船下不来** | `only` 走「一格窗记账制」（靠 legend 的 `ride` 开窗），不要靠 `only` 放宽 tile 名 |
| 3 | `tryBoard()` 靠 `VEHICLES[k].board === tile` 比对；母文件给火輪的 `board` 是 `null` | `null === undefined` 永远不成立 → **火輪根本上不了车**，山顶两个宝箱（含新增的第 24 件神话装）走不到 | 火輪要有真实的登机点 tile |
| 4 | `v.fly` 直接放行任何非 solid 格 | 火輪能飞过地图外框那圈 `T`，绕过 `chuhuo_gate` 的剧情关卡（【agent】报的，我没独立复核这条走位模拟） | `fly` 要排除地图外框 |

## 4. 各份规格的必修项

### 4.1 五分車 + 竹田庄（【agent】判：修 8 处，2 处 blocking；估 6–8h）

- **【agent】blocking：`overworld.json` 整个文件不在改动清单里**。§0 说新入口在 `(28,29)`，
  但 §1 文件清单一次都没提 overworld.json，没有 rows diff 也没有 warp 事件 →
  `tests/cases/maps.js` 的 `地图联通` 断言 `seen.size === maps.length` 会 `31 !== 32` **必红**，
  竹田在游戏里完全进不去。（`交通与世界移动.md` §4.3 原文早就警告「每一张新图都必须挂在 warp 图上」，
  规格引用了同一份文件的其他四节却在这节翻车。）
- **【已核】blocking：内埔站放 `(27,4)` 是错的**。规格把那格描述成「北郊空地」，
  实际 legend 是 `{"tile":"grass","encounter":true}`。【agent】量的结果：从月台出发不踩遇敌格
  能走到的格子数 = 1（月台自己）；走路去竹田 26 步 vs 坐车 24 步，省 2 步换一次遇敌掷骰。
  建议改到 `(17,4)`（紧邻主街 `p` 的 `(16,4)`）——**注意 `(17,4)` 本身也是 `g`/encounter**，
  但站点格会被换成 `railstop` 瓦片，且它贴着零遇敌的主街。
- **【agent】杂货摊柜台在几何上是死的**：`FieldScene.js:200` 的隔柜台特判要求玩家站得到柜台
  这一侧，而 §2.2 把那一侧指定成 solid 的 `^`。照 village.json 青草摊的实际做法
  （街道→柜台→摊主 三格一线）重排。
- **【已核】竹田该有忠義祠**。`data/lore.json` 三处把忠義祠绑在竹田（第 399 行「忠义祠（竹田）
  做中继点」、第 560–561 行「土 · 內埔與竹田 / 竹田庄、忠義祠」），`summons.json` 第 762 行
  写义民爷「请得动：第二幕 竹田忠義祠」。而规格的竹田没有忠義祠，§7.2 还宣称「竹田本身没有
  任何主线/支线关键内容」。**建这座镇就该带上忠義祠**，否则等第二幕再回头改地图。
- **【agent】其余**：`sw.js`/`gen_sw.py` 不在清单（cache-first + VERSION 不变 ＝ 导演手机上
  永远看不到更新）；备选怪福寿螺会打红 `每只怪都能取到自己的美术`；竹田 20 行只给了 3 行；
  `terrain.js` 的 NO_TOUCH 主文件明文要求却没做。
- **【agent】难度参照系这次干净**：不放宝箱、不放装备、商店 4 项是內埔 7 项的真子集、
  复用 `village_field`。姊妹批次（六座迷宫）那两个病灶不成立。33 句新台词跑过真 `wrapText`，
  最长 1 行 230px，离 3 行上限很远。

### 4.2 竹排 + 退潮沙洲（【agent】判：修 11 处，5 处硬伤；估 8–12h）

- **【已核】`tests/cases/art.js` 的「每只怪都能取到自己的美术」无条件扫 `data.enemies`**，
  新增 `fiddlercrab`/`shipwreck` 而 manifest 没有对应图 → **必红**，
  且 `render.js:55`→`draw.js:23` 的 `artW(undefined)` 会让战斗画面**当场 TypeError**。
  这条测试根本没出现在规格 §7.1 那张「逐条核对：不会变红」的表里。
- **【已核】`manifest.json` 里 `raft` 命中 0**（`oxcart` 有）。`FieldScene.js:361` 按
  `raft_down_0` 取图没有兜底 → **6 张竹排母版不是顺带美术，是验证前置**：
  规格 §0 说「唯一验证方式是 `?debug` 设 `state.vehicle='raft'`」，那样做会直接崩。
- **【已核】`sprite:"granny"` 不存在**（manifest 命中 0；`house_hakka.json` 有个 **NPC id**
  叫 granny，不是 sprite）。走到那格会崩，**没有任何测试查 NPC 的 sprite id**。
- **【缺件】`tideflat.json` 的 22×16 `rows` 根本没交付**。四条最吃数据的地图测试因此无从验。
- **【agent】数值参照系讲错但数值本身合理**：`def=14 全场最高` 错（earthox 24、knight 16）；
  `spd=4 全场最慢` 错（slime/earthox 都是 3）。
- **【agent】`raft.only` 不含 `bridge`** → 河被桥切成东西两段，竹排唯一的窗在**西**段，
  而母文件把竹排的叙事起点放在**东港（东侧）**。三份都没发现这条。
- **【agent】规格对的地方**：所有代码锚点逐字存在（不会 `replace()` 落空）；`ZONE_BG` 那条
  隐藏红灯诊断正确；`wreck`→CASTER、`dock`→NO_TOUCH 都判对；§5 美术规格全部核对正确。

### 4.3 火輪 + 山顶彩蛋（【agent】判：修 6 处；估 7h，机制若已由别的任务做完则 2.5h）

- **【agent】`acc:18/crit:12` 数值失衡**：现有 10 件饰品**没有一件**写过 `acc` 或 `crit`
  （这两个字段只出现在武器上），所谓「参照现有饰品档位」不存在。且
  `hitCount = 1+floor(acc/50)` 是阶梯函数：lv20 拳头师 89→107 acc = 2 段变 3 段（**+50% 物理输出**），
  青草婆/符仔仙 1 段变 2 段（**+100%**）。
- **【agent】小地图泄密比规格说的大**：未开宝箱一律画金点，规格那行 `t==='mountain'` 的修法补不到。
- **【agent】可达格数是 857（+4）不是 858（+5）**：规格把宝箱格算进去，却在同一句话里说宝箱格
  不计入 `seen`——证明这一项是手推的、没真的重跑。
- **【agent】`(9,1)` 宝箱嵌在 solid 山壁里**：全库 184 个宝箱**没有一个**在 solid 格上，
  「本来就允许」是编的。
- **【agent】规格对的地方**：`drawShadow` 签名/`SUN` 常数/两个调用点引文一字不差；
  「没有火輪走不上去」（彩蛋门槛成立）用带 `ride` 判定的 BFS 验过；对话 3 行它说「验不了」，
  agent 跑真 `wrapText` 验了，13 句全部只有 1 行（最宽 210px），不用担心。

## 6. 建议的实作顺序

**先修地基，再做内容**——第 3 节那四个 bug 是三份共用的，任何一份先落地都会踩到：

```
第 0 步（地基，约 1–2h，无美术依赖）
  ├ vehicles.js 一次写好 raft + wheel 两条表项（不碰 FieldScene.js）
  ├ overworld.json：legend 定 r=raft/m=wheel，vehicles 一次写成三元素
  ├ w 加 encounter:true
  ├ fly 排除地图外框
  └ 火輪给一个真实的登机点 tile（board 不能是 null）
     → 验：lint 三项 + 96 条测试仍全绿

第 1 步 五分車 + 竹田庄（含忠義祠）  ← 母文件顺序的第 2 级，且不依赖水/飞
第 2 步 竹排 + 退潮沙洲 + 沉船       ← 依赖第 0 步的水域改动
第 3 步 火輪 + 山顶彩蛋              ← 依赖第 0 步的 fly 修正
```

美术（6 张竹排 + 6 张火輪 + 2 只新怪）可以和第 1 步并行出图，它们互不冲突。

**每一步都要走完 `CLAUDE.md`「验收：什么叫改好了」那四步**——特别是第 3/4 步（发布 + 在线上确认），
导演玩的是 GitHub Pages 那份。
