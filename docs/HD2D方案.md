# 歧路旅人（HD-2D）风格：可行性判断与执行路线

调研日期 2026-09-07。**这份文档只做判断和排期，没有改任何代码。**
所有数字都是在这个仓库上实测出来的，测法与复核方式写在最后一节。

---

## 结论一句话

**能做到「一眼看出是受歧路旅人启发」，做不到歧路旅人本身**——3D 地台、法线打光这两条硬性做不到；
而导演现在看到的「杂乱」，八成的改善来自三件几小时就能干完的事，**跟 HD-2D 技术一点关系都没有**，
是这批新瓦片自己的问题。先修那个，再谈风格。

---

# 一、【最急】迷宫地面杂乱：根因与三种修法

导演说的那两张图就是 **`data/maps/fort_ailiao.json`（隘寮石城）和 `data/maps/tomb_wanjin.json`（万金古塚）**——
`data/config.json` 的 `maps` 里一共十二张，只有这两张用了新出的那批物件瓦片。

## 1.1 根因有三层，导演只看到了第一层

### 第一层：每张物件瓦片自带一层地面，而且各自不同（导演的判断，实测坐实）

`assets/art/tile_*.png` 全部 39 张，**边框一圈没有一个透明像素**——每一张都是满铺不透明的。
量每张物件瓦片「底部 30% 的平均色」（那就是它自带的地面），和它实际所在房间的地板比：

隘寮石城的地板是 `flagstone`（全图均色 105,102,97），铺了 **309 格**。摆在上面的是：

| 物件 | 格数 | 自带底的均色 | 最像哪种地板 | 与 flagstone 的 ΔRGB |
|---|---|---|---|---|
| `altar` 祭坛 | — | (190,192,179) | sand 沙地 | **257** |
| `pillar` 廊柱 | 8 | (167,167,154) | sand 沙地 | **184** |
| `carpet` 地毯 | 22 | (179,135,119) | path 土路 | 129 |
| `throne` 王座 | 3 | (134,137,134) | flagstone | 101 |
| `crate` 木箱 | 8 | (126, 84, 45) | floor 木地板 | 91 |
| `stove` 灶台 | — | ( 79, 56, 37) | cave_floor | 132 |
| `idol` 神像 | — | ( 41, 53, 62) | cave_floor | 148 |
| `arch_door` 门洞 | 20 | ( 83, 81, 77) | cave_floor | 63 |

**一个房间里同时有铺石、沙地、土路、木地板、洞窟地面五种地面在打架。** ΔRGB 满值是 765，
184 和 257 是「一眼就看得出是两块地」的量级。导演的定位完全正确。

### 第二层：这批新瓦片和老瓦片根本不是同一种画法（这一层更要命）

把每张瓦片的 RGB 量化到 64 级再数独立色数（低 = 硬边平涂的像素画，高 = 连续调渲染）：

```
老瓦片（像素画档）    flagstone 36   cave_floor 64   cave_wall 77   path 87   wall 88   grass 109
新瓦片（连续调档）    pillar 461   altar 495   idol 565   rubble 663   arch_door 774
                     carpet 783   stove 1010   ore_vein 1016   crate 1029   throne 1398
```

**同一个房间里，地板是 36 色的平涂，柱子是 461 色的连续调，王座是 1398 色。**
就算把地面颜色全统一了，这两种语言并置照样读作「乱」。

原因查到了：`tools/gen_art.py` 第 208 行

```python
out = pixel.process_sprite(w, h, px, tw, th, anchor=..., key=x['kind'] != 'tile')
```

瓦片一路跳过抠底；而且**这批新瓦片压根不在 `gen_art.py` 的 `TILES` 表里**
（那张表只有 23 张老瓦片），它们是从 `tools/art_receiver.py` 的回传通道直接落盘的，
`pixel.process_sprite` 的 `posterize()` / `outline()` 一步都没走过。

### 第三层：这两张地图没有任何统一色调（成本最低、收益最直接的一刀）

`src/field/ambience.js` 的 `MOOD` 表：

```
有 MOOD 的 10 张：village overworld cave_1 cave_2 cave_3 bogong house_elder house_hakka inn shop
没有 MOOD 的  2 张：fort_ailiao  tomb_wanjin        ← 正好就是导演说乱的那两张
```

别的地图都有 `tint`（multiply 调色）+ `vig`（径向压暗）+ `motes`（气氛粒子）把画面收拢，
这两张什么都没有。**几种打架的地板，连一层统一的色调都没给它们盖上。**

## 1.2 三种修法的比较

### ① 物件瓦片改透明背景，构建时合成到该房间的地板上

**机制已经存在，但对现有 PNG 自动抠底行不通——我实测过。**

`src/assets/terrain.js` 的 `SEAMABLE` + `src/assets/terrainBake.js` 的 `keyOutGround` / `seamTile`
就是干这个的：树、水晶、村落现在就是「抠掉自带的底，换成邻居用的那种地面」，宝箱走 `objectTile`。
按理说把 `throne` `crate` … 加进 `SEAMABLE` 一行就完事了。

**但 `keyOutGround`（`tol=18`，从边框均色漫水）在这批瓦片上十张里十张失败：**

| 瓦片 | tol=18 抠出比例 | tol=32 | tol=48 |
|---|---|---|---|
| `pillar` | 4.5% ✗太少 | 11.3% ✓ | 60.0% ✓ |
| `throne` | 3.6% ✗ | 8.3% ✗ | 63.3% ✓ |
| `altar` | 0.2% ✗ | 2.8% ✗ | 14.9% ✓ |
| `carpet` | 0.0% ✗ | 1.1% ✗ | 2.4% ✗（永远抠不出来） |
| `idol` | 7.0% ✗ | 77.9% ✓（**把神像自己吃掉了**） | 95.3% ✗太多 |
| `ore_vein` | 5.3% ✗ | 64.5% ✓（同上） | 92.6% ✗ |
| `cave_floor`（对照） | 21.7% ✓ | **99.9%**（整格吃光） | 99.9% |

`keyOutGround` 的 `frac < 0.10 || frac > 0.90 → return null` 那道闸把它们全挡了，
放宽容差又立刻吃进物件本身。**原因就是第二层**：地面本身的色差已经超过 18/255，
一放宽就分不清「地面的深浅」和「物件的深浅」。

**所以①要成立，必须是「重新出图 + 洋红底」，不是「对现有 PNG 自动抠」。**
这条路管线**已经完全支持**：`gen_art.py` 的 `MAGENTA` 常量、`pixel.chroma_key`、
`process_sprite(key=True)` 全都在，只是瓦片那一支被 `key=x['kind'] != 'tile'` 关掉了。

- **工作量**：十来张物件瓦片各重出一次图（现有回传通道，每张一分钟量级）
  + `gen_art.py` 加一类 `'object'` kind（走 `key=True`、洋红底提示词）
  + `terrain.js` 的 `SEAMABLE` 加名字。
- **对 `data/maps/*.json` 图例格式的影响**：**一个字不改。** 瓦片名不变，`legend` 不变。
- **经得起以后加瓦片吗**：最经得起的一条。以后每加一张物件，只要出图时用洋红底，
  剩下的（合成到哪种地面、要不要落影、要不要镜像）全自动。

### ② 重新生成时统一指定同一种地面

- **工作量**：只改提示词（`… standing on the same grey flagstone floor`），重出十来张图。
  **不动代码、不动数据、不动测试。** 半天内可以让导演看到变化。
- **对图例格式的影响**：零。
- **经得起以后加瓦片吗**：**不行。** 它只解决「这一批、这一种地板」。
  三地门环庙用铺石、牡丹坑主巷用毛面地（`cave_floor`）、伙房用木地板——
  同一个王座要出三份，瓦片数会按「物件 × 地面」相乘。
  而且它**完全不解决第二层**（两种画法并置）。
- **定位**：当天见效的**止血**，不是终局。

### ③ 地板层 + 物件层，两层瓦片渲染

- **对 `data/maps/*.json` 图例格式的影响（这是本方案唯一真正动数据的）**：
  `legend` 的 `{tile, solid?, encounter?, counter?}` 要变成 `{floor, obj?, …}` 或加一个 `over` 字段。
  十二张地图全要改，`tools/gen_dungeon.py` 的 `ROLE` 表（`dungeon_kit.py`）输出也要改。
- **代码工作量的真正所在不是渲染那一行**，而是 `src/assets/terrain.js` 的 `buildTerrainFx`：
  `FRINGE` / `CASTER` / `NO_TOUCH` / `WETTABLE` / `DECO` / `MIRROR` / `SEAMABLE` **七张表**
  全部建立在「一格只有一种 tile」上，每一张都要决定「看的是地板还是物件」。
  渲染侧反而便宜：`FieldScene.render` 内层循环多一次 `drawArt`，满屏约 250 格多 250 次 `drawImage`，
  这个量级实测在预算内（整帧现在只有 1.9 ms）。
- **会打红哪些测试**：
  - `tests/cases/art.js`「地图图例引用的瓦片都取得到」——按 `def.tile` 遍历 legend，字段改了就红
  - `tests/cases/maps.js` 五条都调 `parseMap`，`cells[].tile` 的形状变了会连带红
  都是「改测试就能过」，但确实要改。
- **经得起以后加瓦片吗**：这是**唯一**能表达「同一个王座摆在铺石上／夯土上／木地板上」的方案。

### 这个项目**刚刚在另一处栽过同一个坑，而且已经用①的思路解决了**

提交 `8cdc04e`（战斗背景改用 Gemini 画的整幅天空与远景）的注释写着：

> 「第一版让整幅画铺满战场，结果生成图**自带的地面**和程序化的地面叠在一起，中间一道硬边——
> **两种地面打架，玩家分不清哪层是能站的地**。……让画**根本不带地面**才是对的。」

这和迷宫瓦片是**同一个 bug 的两个实例**：生成的美术自带了一层它不该带的地面。
那边的解法是「出图时就不要画地面」——**那正是①**。
两处用同一条规则收口，比给瓦片单开一套机制干净得多。

### 推荐

**② 今天止血 → ① 这周做正解 → ③ 等到真的需要「同一物件配多种地面」时再上。**

理由：①做完之后③的增量很小（①已经把物件和地面分开了，③只是把「配哪种地面」从自动猜改成数据指定）；
反过来**先做③而不做①是白做**——两层里上面那层还是不透明的满铺图，什么都没解决。

# 二、诚实的可行性判断：HD-2D 的每一条手段，这个项目能不能做

前提：2D Canvas 2D context、逻辑 256×224、ART=6（画布 1536×1344）、零依赖零构建、要跑手机。

| HD-2D 手段 | 判断 | 说明 |
|---|---|---|
| 景深虚化 | **能近似** | 见下 ① |
| 倾斜移轴 | **能做，性价比最高** | 见下 ② |
| 强方向光 | **战斗背景已经做到了；地图上还差一半** | 见下 ③ |
| 泛光 bloom | **技术上做得到，但不该做** | 见下 ④ / 第五节 |
| 法线贴图打光 | **做不到。放弃。** | 见下 ⑤ |
| 3D 几何的地台与高低差 | **做不到。只能画出「假高差」。** | 见下 ⑥ |
| 体积光 | **能做一束，不能做一片** | 见下 ⑦ |
| 粒子景深 | **已经有一半，补齐是零成本** | 见下 ⑧ |
| 镜头微推 | **能做，接口已经留好了** | 见下 ⑨ |

**① 景深虚化——能近似，但别用 `ctx.filter`。**
Canvas 2D 有 `ctx.filter = 'blur(Npx)'`，实测可用。但有个反直觉的坑：**小半径反而更贵**。
在这台机器上，全屏 `blur(4px)` 的增量比 `blur(10px)` 大好几倍——因为 Skia 对大 sigma 走的是
「先降采样再模糊」的近似路径，小半径走的是老老实实的卷积。
所以正确做法是**自己降采样**：画进 1/4 离屏再 `imageSmoothingEnabled=true` 放大回来，
实测增量 +0.15 ms（整帧基准 0.68 ms）。
**根本限制**：俯视网格地图没有真正的深度轴，只能做屏幕空间的移轴。那是「像 HD-2D」，不是「是 HD-2D」。

**② 倾斜移轴——投入产出比最高的一条。**
上 22% / 下 14% 两条带虚化，一下就有「这是个摆在桌上的立体模型」的味道。用①的降采样做法，几乎免费。
**唯一的坑：必须画在 UI 之前**——糊掉对话框文字就是 bug，而地图名条、小地图、菜单都在
`FieldScene.render` 的最后几行。

**③ 强方向光——战斗背景已经做得很好，地图上缺一半。**
`src/battle/backdropDraw.js` 的 `LIGHT` / `SHAFT` / `ridge(edge)`、`src/assets/tiles.js` 屋顶那整套
「正脊→瓦面→檐口→墙身→石脚」的明暗序，都严守「全场只认一个光向」——这已经是 HD-2D 的做法了。
地图上缺的是：`src/assets/terrain.js` 只有崖影（`shadowTile`，压暗 N/W/NW 三个方向），
**没有对称的受光边**。补一张 `litTile`（东/南侧描一道亮边）是对称的一小步，收益立竿见影。

**④ 泛光 bloom——做得到，但按这个项目的规矩不该做成后处理。**
`src/battle/fxKit.js` 文件头那三条（峰值 ≤0.45 / 起落各 ≥0.08 秒 / 一个法术只闪一次）是硬规矩，
而 bloom 的本质就是「亮的地方更亮并往外溢」，逐帧跟着亮度走，天生是「亮度在变」，最容易踩线。
**可做的是静态 bloom**：把光源那一格的亮部烘进瓦片（走 `terrainBake.js` 的 `baked()` 缓存），
不逐帧算，也就不可能闪。地图上的宝箱微光已经是这个思路的合法版本（2.4 秒周期、`lighter` 加色、局部）。

**⑤ 法线贴图打光——做不到，明确放弃。**
没有法线数据、没有 WebGL、canvas2d 没有逐像素着色器。两条替代路都是死路：
每帧 `getImageData` 逐像素算光照（满屏 206 万像素，绝无可能，而且见第五节第 6 条）；
或者预烘 N 个光照方向的瓦片副本（内存 ×N，而且地图上的光源是**移动的主角**，方向连续变化）。

**⑥ 3D 地台与高低差——做不到，这是 HD-2D 最核心也最贵的一条。**
歧路旅人的地台是真 3D 网格，摄影机有俯角，角色上台阶时 y 和 z 是分开的。
这个项目是 16px 网格 + `cells[y*w+x]`，**没有高度轴**，碰撞是网格制
（`CLAUDE.md` 禁止条：「像素级碰撞（一律网格制）」）。
**能近似的只有「把高度画出来」**：`tiles.js` 的房子那一套（`roof_ridge`→`roof`→`roof_eave`
→`wall_upper`→`wall_base`）已经是一条竖直的明暗序了，配上 `terrain.js` 的崖影，
读起来确实有高度。要更进一步就是给墙和台地画出「侧面」——那是**美术活**，不是引擎活。

**⑦ 体积光——已经有一束了。**
`backdropDraw.js` 的 `drawCave` 里那道天光（斜切变换 + 线性渐变，注释写明是「全文件唯一允许
边缘发虚的地方」）就是体积光，做得很对：4.6 秒周期、亮度只在 ±14% 浮动。
再加要守同一个分寸，而且**地图上加光柱要格外小心**——它是全屏范围的加色，正是防闪规则盯着的东西。

**⑧ 粒子景深——已经有一半。**
`ambience.js` 的 `makeMotes` 已经有 `par`（视差，0.55~1.0）字段，跟镜头走得慢的显得远。
缺的只是「远的更淡更糊」：给 `par` 小的粒子配更低的 alpha 和 2×1 而不是 1×1 的方块。纯静态，零成本。

**⑨ 镜头微推——接口已经留好了。**
`backdropDraw.js` 的 `paintScene(ctx, W, bg, t, panX = 0)`，注释里明写「留给出手时镜头推一下的接口，
现在没人传」。地图那边要注意：`FieldScene.render` 的 `camX/camY` 用的是 `Math.round`（逻辑像素取整），
做微推得换成 `snap()`（物理像素精度），否则会一格一格跳。

# 三、验证「高分辨率场景 + 低分辨率角色」这个杠杆

**判断：方向对，但你说的那个具体机制不成立——不是因为难，而是因为这一步已经做完了，而且余量已经用光。**

## 3.1 三条实测

**（a）「背景被降采样到逻辑网格」不成立。**
`src/core/draw.js` 的 `drawArt` 是 `ctx.drawImage(img, x, y, img.width / ART, img.height / ART)`，
而 ctx 挂着 `setTransform(ART,0,0,ART,0,0)`。两下抵消：一张 96×96 的瓦片落到画布上**正好是
96×96 物理像素，1:1，没有任何降采样**。地形层从第一天起就是按物理像素画的——
`terrainBits.js` 那套 `u()` / `us()` / `PX` 换算就是专为这个存在的。
「背景不再降采样到逻辑网格」这一步**没有可改的东西，因为它从来没有降采样过**。

**（b）母版的余量只有 1.33×，不是「甚至更高」。**
`assets/art/master/` 的实际尺寸：瓦片 **128×128**、角色 **128×192**、敌人 512×512。
`tools/set_art.py` 的文档字符串把这条写得很直白：

```
ART=6  画布 1536×1344  角色  96×144  瓦片  96×96
ART=8  画布 2048×1792  角色 128×192  瓦片 128×128   （母版精度，再高就得重新出图）
```

所以能提的只有 **6 → 8**，线性 1.33×。（敌人是例外，512 母版对 216~384 成品，那边余量大一些。）

**（c）提到 ART=8 是纯亏。**

*屏幕根本放不下。* 按 `src/core/Game.js` 的 `fitCanvas()` 算实际设备像素宽度：

| 设备 | canvas CSS 宽 | 实际设备像素宽 | ART=6 的 1536 够不够 |
|---|---|---|---|
| iPhone 13/14 横屏 | 446 | **1338** | 够，还多 198 px 被压掉 |
| iPhone 15 Pro Max 横屏 | 491 | **1473** | 够 |
| Android 中端 2340×1080 横屏 | 411 | **1233** | 够，还多 303 px |
| iPad Pro 11 横屏 | 953 | 1906 | 不够（缺 370） |
| retina 笔电全屏 1512×945 | 1024 | 2048 | 不够（缺 512） |
| 4K 桌面 | 2304 | 2304 | 不够（缺 768） |

**手机上现在的画布已经是被压着显示的，多出来的像素一个都看不见。** 只有平板和大屏有缺口。

*代价 1.83×。* 同一份工作量（满屏瓦片 + 0.4 张/格叠加 + multiply 压暗 + 全屏调色 + 径向暗角）：

```
ART=6  1536×1344 (2.06 Mpx)   11.03 ms
ART=8  2048×1792 (3.67 Mpx)   20.16 ms      → 1.83× 帧耗时（像素数 1.78×）
瓦片基图缓存 1.7 MB → 2.9 MB（还没算 terrain 的烘焙缓存，那部分是按邻居组合缓存的，会更多）
```

*而且会连带打红测试。* `tests/cases/art.js`「角色与瓦片的美术尺寸必须正好是 逻辑尺寸 × ART」
要求所有素材同步重新派生，漏一张就红；`tools/set_art.py` 的 `stale_masters()` 还会跳过
它判定为「过期」的母版（实测这个判定救过一次，把修好的美术差点退回旧设计）。

## 3.1b 补记：这个杠杆**刚刚被人拉过一次**（提交 `8cdc04e`，就在我做这份调研的当口）

`8cdc04e 战斗背景改用 Gemini 画的整幅天空与远景` 把战斗背景的天空 + 远景两层换成了整幅画：
`assets/art/bg_{plains,cave,deep,shrine}.png`，各 **512×240**，`assets/art.js` 里单独一张
`backdrops` 表，`tools/set_art.py` 加了 `is_bg()` 让它**不走派生、直接用母版**。

**这条路之所以走得通，正是因为它绕开了 ART 的天花板**——值得写清楚，因为它是本节唯一的例外：

> 瓦片和角色被 ART 锁死（`tests/cases/art.js` 明文要求「尺寸必须正好是 逻辑尺寸 × ART」），
> 而**整幅背景不是按格子铺的**，它的母版想画多大画多大，绘制时拉到目标框就行。
> 所以「用母版精度画背景」对**整幅画**成立，对**瓦片**不成立。

**但现在这一版有一个立刻能修的问题**：`backdropDraw.js` 的 `plate()` 里写着

```js
ctx.imageSmoothingEnabled = false;
ctx.drawImage(im, -M, -M, W + M * 2, hz + M);
```

512 宽的画被拉到 `W + M*2 = 268` 逻辑 = **1608 画布像素，放大约 3.1 倍，而且是最近邻**。
于是每个源像素变成一个 3×3 的硬方块——**同时拿到了「绘画的糊」和「最近邻的块」，两头的短处**。
一幅连续调的画正是这个项目里**唯一**该开平滑的东西（瓦片和角色绝对不能开）。两条路选一条：

- 把这一处改成 `imageSmoothingEnabled = true`（改完记得在离开前恢复 false，别污染后面的精灵绘制）；**或**
- 把母版按画布实际尺寸重画（1536 宽而不是 512）——文件会大不少，但一劳永逸，且和「母版精度」的说法才对得上。

（这条不在我的路线表里，因为它是**别人正在改的文件**。建议直接转告那位，不要两边同时动
`backdropDraw.js`——它一直贴着 400 行的上限，我调研期间它在 361 / 396 / 420 行之间变过三次。）

## 3.2 那真正的杠杆在哪：**在「调子」，不在「分辨率」**

HD-2D 的视觉对比**不是像素多少**，是「**连续调、有光照的场景** vs **硬边平涂的角色**」。
这个项目现在的状况恰好卡在中间，而且两头都不对：

```
老地板瓦片    硬边平涂     flagstone 量化后 36 色      ← 太「像素」
新物件瓦片    连续调       throne 1398 色              ← 已经是 HD-2D 的调子了
角色          两头不靠     master 88 色 → 游戏用的 669 色
```

角色那一行是查出来最有意思的一条：**成品比母版颜色更多。**
`tools/set_art.py` 的 `derive()` 只做 `downscale` + `threshold_alpha`——
**没有 `posterize`、没有 `outline`**（而 `gen_art.py` 的 `process_sprite` 是有的）。
面积平均缩小会重新引入中间色，于是母版 88 色的平涂角色，落到游戏里变成 669 色的糊图。
**角色现在既不够「像素」，又不够「精细」。**

所以真正该做的那一步是（**零引擎改动、零渲染路径改动、文件尺寸不变**）：

- **角色往「更硬」走**：`derive()` 对 `char_*` 补回 `pixel.posterize()` + `pixel.outline()`；
  更彻底的做法是把母版先缩到 32×48、量化、再**最近邻**放大回 96×144，
  得到「3 个物理像素 = 1 个美术像素」的块感——那正是歧路旅人角色的样子。
- **场景往「更软」走**：地板瓦片按新物件瓦片那种连续调重出，并统一光向。

## 3.3 代价（导演问的每一条）

| 你担心的 | 实测结论 |
|---|---|
| 性能 | **零。** 改的是离线派生出来的 PNG 内容，不是渲染路径。 |
| 内存 | **零。** 文件尺寸不变（`char_*` 仍是 96×144，`tile_*` 仍是 96×96）。 |
| 与 `snap()` / 物理像素对齐的冲突 | **零，而且是加分。** 角色变块之后，`snap()` 那套「最小步长 1 物理像素」的好处才真正显出来：块状角色在细腻背景上**平滑**移动，正是 HD-2D 的招牌。 |
| 瓦片接缝 | 地板改连续调后，`MIRROR`（水平镜像破周期）和 `FRINGE`（咬合）都仍然成立。但 `keyOutGround` 会更难用（见 1.2 ①），所以**物件必须走洋红底那条路，不能指望运行时自动抠**。 |
| 手机 | **零成本。** 像素数、绘制次数、合成模式切换次数全都没变。 |
| 测试 | `tests/cases/art.js` 的三条角色体检（尺寸一致 / 身高一致 / 站姿与迈步同体型）判的是**实心面积**和**高度比例**，量化不改这两者，应当仍然过——但上线前要真跑一次。 |

# 五、不要做的事（看起来像 HD-2D，但对这个项目是陷阱）

1. **全屏 bloom / 辉光后处理。**
   `src/battle/fxKit.js` 文件头那三条（峰值 ≤0.45、起落各 ≥0.08 秒、一个法术只闪一次）是真规矩，
   光敏性风险是真的；`Game.renderMosaic` 里还留着「全项目最后一处真·高频闪烁」被改掉的注释。
   bloom 逐帧跟着亮度走，天生就是「亮度在变」，最容易反复推过 0.45。
   **要泛光就烘进瓦片（静态），不要做后处理。**

2. **把体积光做成一片会动的光。**
   `drawCave` 那束是安全的（4.6 秒周期、±14%）。再加必须守同一个分寸：
   周期 ≥3 秒（`tests/cases/art.js`「瓦片动画的循环周期不能太快」卡的就是这条）、振幅 ≤0.2。

3. **用 `ctx.filter` 做小半径模糊。**
   实测 `blur(4px)` 比 `blur(10px)` 贵好几倍——Skia 只有大半径才走降采样近似。
   **要模糊就自己降采样。**

4. **提高 ART。** 第三节：手机上一个像素都看不见，代价 1.83×。

5. **指望运行时 `keyOutGround` 抠这批新瓦片。** 第一节：十张里十张失败或抠过头。

6. **每帧 `getImageData` 做逐像素处理**（法线光照、色调映射、真 bloom）。
   **这条我自己在做这份调研时踩了**：连续 `getImageData` 会让 Chrome 把画布从 GPU
   降级成软件光栅，同一份渲染从 ~2 ms 变成 60~80 ms，而且**降级之后不会自己恢复**。
   这不是理论风险，是这台机器上实测出来的（也是这份文档里数字改过一轮的原因，见下）。

7. **在没有缓存的矢量背景上叠后处理。**
   `backdropDraw.js` 的写景是逐帧几百次 `fillRect` + 若干全屏渐变（`8cdc04e` 之后天空和远景
   换成了整幅画，中景近景仍是矢量）。实测**全屏渐变填充比纯色填充贵一个数量级以上**，
   而 `fillAll` / `band` 还都往画布外多铺 6px（震屏留边），出界的渐变填充还要再贵一截。
   **先缓存（或换成画），再叠特效**，顺序反了就是把成本乘起来。

8. **破 400 行。** `backdropDraw.js` 现在就在这条线上晃，`FieldScene.js` 344、
   `terrainBake.js` 298、`tiles.js` 387 也都在逼近。**这一轮所有新东西都开新文件。**

9. **引入依赖或构建步骤**（three.js / pixi / 任何后处理库）。`CLAUDE.md` 禁止条第一条。

# 六、这些数字是怎么量的 / 导演该怎么复核

**环境**：这台 Mac / Chrome / 画布 1536×1344 / DPR 2 / CSS 768px
（也就是 **1 画布像素 = 1 设备像素**，桌面上正好 1:1）。

**手法**：连续调 N 次 `game.render()` 量墙钟，**全程只在最后读回一次像素**。

**一个重要的教训**（也解释了为什么这份文档的性能数字比第一版低一个数量级）：
我一开始每次迭代都 `getImageData` 强制同步，量出「地图 8 ms、战斗 80 ms」这样的数字，
按那个数字写出来的结论会是「战斗画面已经在掉帧，不能再加任何东西」——**那是错的**。
交叉验证发现是 `getImageData` 把画布降级成了软件光栅。换成「只在最后读一次」之后：

```
地图 fort_ailiao   ≈ 1.9 ms/帧   （60fps 预算的 11%）
战斗画面           ≈ 0.9 ms/帧
```

**桌面上有大约 14 ms 的余量，所有后处理方案的增量都在 0~2 ms，彼此差异接近这台机器的测量噪声。**
所以选型该看**做法**（降采样 vs `ctx.filter`、缓存 vs 逐帧）而不是我这几个小数点。

**手机没量到**（浏览器窗格是隐藏的，截图和 rAF 都不可用）。请在手机上按这个顺序验：
开 `?debug` 看左上角 FPS →（一）在隘寮石城走一圈 →（二）打一场普通遇敌 →（三）放一次全体魔法。
**任何一步看到 FPS 掉到 58 以下就停，那一步就是预算边界。**

**没有留下任何临时文件**：这次没有创建 `tests/_hd2d_probe.html`，验证全部通过
`javascript_tool` 在运行中的页面里注入完成。改动只有这一份 `docs/HD2D方案.md`。
