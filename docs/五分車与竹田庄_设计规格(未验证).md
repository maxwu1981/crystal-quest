# 五分車（第二级载具）+ 竹田庄 —— 设计规格

> 项目：`/Users/barry/Projects/crystal-quest`。本文档为纯设计规格，未修改仓库任何文件（全程只用 Read/Bash 只读查证）。所有坐标、现有 JSON 内容、测试规则均已对照仓库实际文件逐一核对（不是凭记忆或凭任务描述里的摘要），核对方法与结果见第 6 节。

## 0. 关键决策一览（先讲结论，理由在后面各节）

| 决策点 | 我的选择 | 一句话理由 |
|---|---|---|
| 竹田在 lore 里的正式名 | 地图 `name` 字段用 **"竹田庄"**，不是"竹田鎮" | `data/lore.json` 的 `regions_beyond` 原文写的是"竹田庄"，跟內埔庄对称；本文档标题沿用你的"竹田鎮"只是口语指称，数据里要对齐既有设定 |
| 地图 id / 文件名 | `zhutian` → `data/maps/zhutian.json` | 与 village/overworld 一样取短英文 id |
| 五分車怎么触发 | **不进 `VEHICLES` 表，不用 `state.vehicle`**，新瓦片 `railstop` + 新函数 `tryRail()`，逻辑上更接近"一个特殊的、内容可变的箱子"而不是"一种骑乘状态" | 五分車是瞬间选单传送，不是"骑着走"的连续移动模式，硬塞进 `state.vehicle:'rail'` 反而要多处理"选完之后怎么下车"这种不存在的状态 |
| 五分車选单的 UI | **复用 `DialogueScene` 现成的 `choices` 机制**，不新写 Menu 场景 | 见第 1.3 节——`DialogueScene.openChoices()` 已经能画任意长度的选项列表并支持"取消＝最后一项"，五分車站点表再长也不用另起一个场景类 |
| 遇敌区 | 竹田直接复用 `village_field`，**不新建 zone** | 竹田与內埔在 lore 里本来就是同一个 region（"土 · 內埔與竹田"），且新建 zone 会牵连 `backdrop.js` 的 `ZONE_BG` 表（有专门测试卡住这件事，见 6.6），不新建=零新增风险 |
| 新怪物 | **不做**（核心交付里没有新怪），文末给一只完全可选的"福壽螺"备选 | 同上，reuse 就够，福寿螺仅供你觉得手感太单调时加 |
| 內埔站放哪 | **village.json 内部**（北郊空地 (27,4)），不放 overworld | 避开你提到的 (20,27) cartstop 那一整簇（cartstop/村门/traveler 已经很挤），站台放进庄子里也更像"车站"而不是"路边一根杆子" |
| 竹田站放哪 | zhutian.json 内部，庄子主路南端的小广场 (15,14) | 与內埔站同一逻辑：站台是庄子的一部分，不是孤零零杵在旷野 |
| overworld 新入口 | (28,29)，'V' 瓦片，六堆平原南侧空地，紧邻现有森林块东侧 | 现状是纯 'g' 空地，未被任何 event/NPC 占用（已用脚本核对，见 6.1），且与內埔村口地理相邻，符合"竹田在內埔旁边"的现实感 |

### 1.6 `src/field/rail.js`（新建，代码，约 25 行）

对照 `src/field/vehicles.js` 里 `tryBoard()` 的写法：

```js
// 五分車：选站即到的选单，本质是 warp；不是 state.vehicle 状态，没有「骑着」这回事。
// 与牛車的分工见 docs/交通与世界移动.md §2.2；这里只接站点表。
import { DialogueScene } from '../ui/DialogueScene.js';
import { audio } from '../core/audio.js';

// 面朝的格子是不是一个五分車站台；是的话弹出「去哪位」的选单。
// 回传 true = interact() 已经处理掉，不用再往下找 NPC/事件——跟 tryBoard 同一个约定。
export function tryRail(scene, x, y) {
  if (scene.cell(x, y)?.tile !== 'railstop') return false;
  const g = scene.game, rail = g.data.config.rail || [];
  const here = rail.find(s => s.map === scene.mapId && s.x === x && s.y === y);
  const dests = rail.filter(s => s.id !== here?.id && g.state.flags[s.flag]);
  if (!dests.length) {
    g.scenes.push(new DialogueScene(g, { pages: ['车路还没通到别位，等別站也通车再来搭。'] }));
    return true;
  }
  g.scenes.push(new DialogueScene(g, {
    pages: ['要坐五分車去哪位？'],
    choices: [...dests.map(s => s.name), '毋去咧'],
    onDone: r => {
      if (r == null || r === dests.length) return;   // 取消＝选到最后一项，跟 runInn 的「不了」同一个约定
      const to = dests[r];
      audio.sfx('door');
      g.fadeTo(() => scene.loadMap(to.map, to.x, to.y, 'down'));
    },
  }));
  return true;
}
```

**为什么不用新写一个 Menu 场景（比主线设计草案原先估的"约 80 行"省了一大截）**：`src/ui/DialogueScene.js` 的 `choices` 参数本来就会在 `openChoices()` 里现造一个 `Menu` 实例，长度按 `choices.length` 自动撑开、超出高度会自动滚动（`Menu.js` 自带 `scroll` 逻辑），`onCancel` 默认选中"最后一项"这个约定 `runInn()` 已经在用（`choices:['住宿','不了']` 配 `if (r!==0) return`）。五分車选单直接复用这一整套，站点再多也不用另起炉灶。

### 2.2 版式说明（整体布局，非逐格画）

南北向长条，比內埔庄窄矮一截：

```
y=0        庄门（北面缺口式围墙，开口在第14列）
y=1..6     北郊田野（可遇敌的 g，稀疏几棵装饰用单株 T，仿內埔庄北郊田的做法）
y=7..8     曬穀埕过渡带（安全的逗号地 , ，路继续穿过）
y=8..13    庄子主体：西侧一户顾田人家的院子（约第2~10列），东侧一个杂货摊（约第17~25列）
y=13..16   车站小广场（安全地 , ，五分車站台在广场中央）
y=17       灌溉水圳（一整排 w，呼应「土」这条线欠的是「田」），主路两格架桥通过
y=18       庄外稻田边缘（装饰用 g）
y=19       南面围墙（无缺口——南边不开门，回 overworld 走北门原路）
x=13-14    两列宽的主路（p），仿內埔庄"pp"双宽路面，从北门一路通到车站广场，
           必须在 y=1..17 之间连续不中断（含水圳处的桥）
```

两栋建筑都不设室内地图，NPC 就站在外面——完全比照 village.json 里"菸楼的头家"（29,20）那种"只站在建筑外面，没有可进入的门"的做法，不必为竹田另开 house 类地图：

- **西侧顾田人家**：约 7 列宽（x=3~9）× 4 行（y=8 屋脊、y=9 檐口、y=10 上墙+窗、y=11 下墙+门），y=12 是门前的踏地阴影（`_` shadow_dirt，可走）。
- **东侧杂货摊**：更小，约 4 列宽（x=18~21），y=9 一段瓦檐 `^^^^`，y=10 一排柜台 `c`（`counter:true, solid:true`，玩家隔着柜台说话由引擎 `interact()` 的 counter 特判自动处理，不用额外逻辑）。

## 4. 怪物 / 遇敌表设计

**核心交付：不新增怪物，不新增遇敌表。** 竹田的 `encounterZone` 直接写 `"village_field"`，复用內埔庄现有的怪物池（魔神仔/海漂/山羌/荔枝椿象/野狼，`data/encounters.json` 里已经配好）。

理由三条：

1. **lore 上站得住**：`data/lore.json` 的 `regions_beyond` 把"內埔與竹田"列成**同一个** region key，不是两个 region，说明设定上它们本来就该共用同一套田野生态，不是各自独立的怪物圈。
2. **零风险**：`tests/cases/data.js` 有条测试专门卡"每个遇敌区都有对应的战斗背景"，逐一收集所有地图的 `encounterZone` 字符串去查 `src/battle/backdrop.js` 的 `ZONE_BG` 表，查不到就红。`village_field` 早就在 `ZONE_BG` 里（`village_field: 'plains'`），新建一个 `zhutian_field` 之类的 zone 就必须同步改 `backdrop.js`，复用则完全不用碰这个文件。
3. **玩家感知不到差异是好事**：怪物池是后台数值，竹田的"这是另一个庄"的实感应该、也已经完全靠 NPC/建筑/对话立住了（第 3 节），不需要靠换一批怪来证明。

## 7. 风险与取舍

### 7.1 会不会打红现有测试

逐条对照仓库现有测试文件（`tests/cases/maps.js`、`data.js`、`art.js` 全文通读过），结论：

| 测试 | 影响 |
|---|---|
| 地图事件与 NPC 格式 | 不受影响——新 NPC/警示 warp 均符合 schema |
| 对话每页最多 3 行 | 低风险，见 6.9 |
| **可达性 reach()** | 内埔/overworld 侧已程序核对零风险；zhutian 侧取决于实现者手绘是否遵守 2.4 节约束，见 6.8 |
| 宝箱 id 唯一/内容合法 | 不涉及——本设计**刻意不给竹田加宝箱**，因为查过 village/house_elder/house_hakka/inn/shop/bogong 六张城镇/室内地图，**没有一张有 chest 事件**，宝箱在这个项目里是"荒野与地城专属"的既有规矩，竹田加宝箱反而是破坏一致性 |
| 落点不能压另一传送格 | 已程序核对两对新 warp 均未与任何既有 event 坐标重叠 |
| 地图联通 BFS | 新增 `village→overworld→zhutian` 这条边后 `zhutian` 必然进入 BFS 可达集合，只要 `config.maps` 加了它、文件存在即满足 |
| 投影源登记 | 零新增 solid tile 类型，零风险（见 2.3 末尾说明） |
| 每个遇敌区都有战斗背景 | 复用 `village_field`，零风险 |
| 敌人数据字段完整 / 遇敌表引用存在 | 不涉及（核心交付无新怪；如采用 4 节备选怪，字段已按 schema 逐项核对） |
| **地图图例引用的瓦片都取得到** | **会打红，除非同一提交里做了 1.4 节的 `DRAW.railstop`**——这是唯一一条"不加代码就必炸"的测试，已重点标注 |
| 画面宽度/wide 场景等 | 与本次改动完全无关的场景类测试，不涉及 |

### 7.2 会不会让主线/支线剧情提前或滞后

- **竹田本身没有任何主线/支线关键内容**（没有 Boss、没有钥匙道具、没有推动 flag 的强制对话），提前到达竹田 = 提前看到几句"另一个庄也在过日子"的环境对话，**不构成剧透或跳出既定叙事节奏**。
- 竹田 NPC 的 `bossDefeated` 分支只是**复述**玩家刚在 cave_3 亲眼打完 Boss 后已经看到的"乌火散成火星"演出的后续影响（田水退、金身裂），属于"世界各地对同一件事的呼应"，跟 `hf_gatekeeper`/`pond_gatekeeper`/`chuhuo_gate` 这几个现成 NPC 反应同一个 `bossDefeated` 的做法是同一套逻辑，**不会造成信息顺序错乱**（玩家不可能在触发 `bossDefeated` 之前就看到这段台词——变体判断天然保证了顺序）。前提是 6.3 节那条验证成立。
- **五分車本身不新增可达性**——两个站台都在玩家早就能走到的地方（一个在庄内，一个在新开的、本来就规划要做的竹田庄），它省的只是"走过去要花的时间"，不打开任何新区域、不跳过任何既定路线，符合 `docs/交通与世界移动.md` §3.2 定的规矩："每一级至少要有一个'非它不可'的地点……但主线绝对不可以卡在载具上"——这次的五分車两站都不构成"非它不可"，纯粹是便利层，风险最低的那一种改动。
- 与现有**牛車**系统零交互：牛車只认 `state.vehicle`/`path`/`cartstop` 这一套，五分車走的是完全独立的"瞬间选单 warp"，两套机制除了都挂在 `interact()` 里之外没有任何共享状态，不会互相干扰（骑着牛車能不能站上五分車月台互动，我没有特别处理——`passable()` 对非 `ride` 格子仍按"骑上载具收窄能走范围"处理，牛車 `only:['path','cartstop']` 不含 `railstop`，所以骑着牛車根本走不到月台格旁边，這是现有机制自动带来的合理限制，不需要额外写判断）。

### 7.3 相对主设计文档（`docs/交通与世界移动.md`）的偏离，及为什么

该文档 §4.4 原本设想五分車需要 **两个** 新瓦片：`rail`（轨道装饰）+ `station`（月台）。本规格**只做了一个**（`railstop`），原因：

1. 五分車是纯选单传送，玩家从来不会"沿着铁轨一格一格走"，`rail` 轨道瓦片是纯装饰、不承担任何机制，而当前只做「站到站的最小可用版本」，装饰性轨道可以完全延后，不影响可玩性，也不影响任何测试。
2. `station`（月台）在本规格里就是 `railstop`——你的任务描述里已经把这两级简化成了一个瓦片的提法（"新增一个'railstop'瓦片"），我按你这次给的指示走，只是在这里明确记一笔"跟主文档 §4.4 的四瓦片清单相比少做了 `rail` 这一个纯装饰瓦片"，避免你以后对着两份文档觉得对不上。
3. 主文档 §6.2 估的"约 80 行"选单代码，本规格因为直接复用 `DialogueScene.choices` 落到约 25 行——这是我在读源码过程中发现的实现层面简化，记在这里供实现者知道为什么行数差这么多，不是漏做了什么。

### 7.4 其它取舍

- **兩個站务员共用同一张 `innkeeper` 精灵**：零新美术换来的代价是"內埔和竹田的车站员长得一模一样"，在这个项目现有的美术经济（大量角色本来就靠复用/借图，`tests/cases/art.js` 里专门有一条"没画美术的职业用 `art` 借别人的图"）下是可接受的一致做法，不是偷懒漏做。
- **竹田不设室内地图**（杂货摊、顾田人家都只是"站在外面"的 NPC）：换来的是不用再多设计、多测试一张室内小图，代价是玩家进不了任何竹田的屋子——参照 village.json 里"菸楼的头家"同款处理，这个项目本来就不要求每个有名字的建筑都能进去。
- **竹田南面不开第二个门**：换来的是站点表/warp 只有一对（逻辑更简单，出错面更小），代价是"竹田只能从北边这一个方向离开"——对一个新开的小庄来说是合理的取舍，以后要往南接新地图（比如书线设计里更靠南的地区）时，可以在竹田南墙再开一个 warp，不影响本次设计。
