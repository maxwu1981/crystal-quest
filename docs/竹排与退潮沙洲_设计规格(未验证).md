# 竹排（三级载具・水）＋ 退潮沙洲・沉船 —— 设计规格

## 0. 范围声明（先说清楚做什么、不做什么）

本规格覆盖：
1. `overworld.json` 河道**西端**开一格"一格窗"（出海口方向），通往新地图 `tideflat`（溪洲仔）。
2. 新地图 `tideflat.json`：退潮沙洲＋沉船残骸，2 个宝箱、1 个 NPC，自洽的一小块可选探索内容。
3. 竹排载具本身：`VEHICLES.raft`、遇敌区 `plains_river`、`tideflat`、两只新怪、`dock`/`wreck` 两个新瓦片的**定义**（tiles.js/terrain.js/minimap.js），以及让这一切真正跑起来还缺的三处引擎代码（`get zone()`、`resetEncounter()`、`walkable()`）。

**明确不做，并说明为什么**（详细论证见第 7 节，这里先给结论）：
- **东端窗口（(38,14)，上溪方向）本次不开。** брief 本身允许跳过；且它的落点在既有的第三幕地图上，我没有被给到具体接哪张图哪个坐标，硬猜风险高于收益，留给知道隘寮溪河床现状的人来接。
- **`dock` 瓦片本次不放置在任何地图上**（overworld 或 tideflat 都不放）。原因见第 7 节——`tryBoard()` 现在没有任何前置条件检查，只要地图上有一格 `dock`，从游戏一开始就能上竹排、划到我们新开的窗口。竹排的叙事时间点是第五幕（東港造船人家给的），两个一格窗又都开在**开场就能到**的六堆平原上，没有牛車那种"地理隔离"保护。所以我只交付"竹排能怎么运作"的机制和内容，不交付"玩家从哪里第一次拿到竹排"——这条留给第五幕東港渔寮的人做，届时只需要在那张图的岸边放一格 `dock`，机制不用再碰。
- **现在验证这套东西的唯一方式是 `?debug` 控制台手动设 `state.vehicle='raft'`**（`交通与世界移动.md` 第 54 行已经写明这条路）。这是有意为之，不是遗漏。

### 7.2 会不会让某条主线/支线剧情提前或滞后

这是本次设计里我认为**唯一需要导演明确表态、不能靠"给默认值"就完全带过**的风险，我按"有默认值先落地、异常处报告"的原则处理如下：

**核心风险**：竹排的叙事时间点定在第五幕（東港造船人家给），但这次要开的两个一格窗（尤其是我选择实现的西窗）都开在 `overworld` ——一张开场第二步就会走到的地图上。牛車能在第一步就摆出来而不破坏节奏，是因为"牛車不新增可达性，只是安宁"（`交通与世界移动.md` 原话）；竹排不一样，它**新增可达性**，一旦有玩家能让 `state.vehicle` 变成 `'raft'`，就能立刻跑来我这次做的沙洲拿两个宝箱、打提前打不到的"沉船的"——这在低强度上"剧透"了第五幕的地理线索（東港沿岸有沙洲、有沉船、有蚵殼招潮蟹这些怪），但**不会**剧透"討替"/"送的法"/秀琴支线这些真正的核心剧情揭示，因为我刻意没有做任何 crystal 事件、没有做 boss、NPC 台词也刻意写得像背景居民而非知情者。

**我的处理方式**（已经在 0 节点明，这里说清楚理由）：**不放置任何 `dock` 瓦片**。`tryBoard()` 现在的实现完全没有 flag/物品前置检查——这是我读源码确认的事实，不是猜测——所以"竹排什么时候能骑"这件事在这套引擎里**完全靠地理隔离**，不靠代码判断。牛車的两个 `cartstop` 之所以能安全地"开场就摆"，是因为它们摆在开场就会经过的干道上、且牛車本身不解锁新地方；竹排如果现在就摆一个 `dock`，等于把"地理隔离"这个唯一的保护机制也拆掉了。所以我把"竹排从哪里第一次骑上"整个留白，交给第五幕東港渔寮的实现者——他们建那张图时，在岸边放一格 `dock`，玩家才第一次有机会在正常游玩中把 `state.vehicle` 设成 `'raft'`。在那之前，这次做的所有内容都只能靠 `?debug` 触达，物理上锁死。

**如果导演认为这个处理过于保守**（比如希望现在就能在正常游玩里测试这条线，或者接受"沙洲内容提前可见"不是问题）：最小改动是在 `overworld.json` 找一处不影响主线动线的角落加一格 `dock`（比如就近西窗放在 `(2,13)`，把该格从 `,` 附近的 `S` 沙地改一格 `dock`），一行 JSON 的事，不需要改动本规格的任何其它部分。我把决定权留在这里，但默认按更保守的方案落地。

**关于"跳过东端窗口"对剧情节奏的影响**：`交通与世界移动.md` 把东端窗口定位成"上溪→隘寮溪河床（第三幕·金）的回程捷径"——纯粹是**捷径**，不是新内容、不是必经路径（第三幕本来就是走路去的）。跳过它这次不做，除了"暂时少一条回程捷径"之外，不影响任何剧情的可达性或揭示顺序，风险最低，这也是我选择优先做西端、明确推迟东端的直接原因。

### 7.3 其它取舍

- **"沉船的"数值取了偏高的参照区间**（见 4.1 末尾），是我这次唯一一处没有完全落在需求文字给出的保守区间内的数值决定，已经明确标注、给出了回退方案，不需要另外验证，是设计判断不是事实错误。
- **两个"渡"字线索会不会太密**：见 2.4 节末尾，已给出可回退的替代文本方向。
- **`plains_river` 与 `tideflat` 拆成两张独立遇敌表、都手写了一份 `groups`**，而不是让 `tideflat` 直接复用 `plains_river` 的表——多了一份要维护的 JSON，但换来"划船"和"上岸走路"两种状态有各自合理的强度曲线（划船能遇到罕见的"沉船的"，走路不会），我认为这个复杂度是值得的；如果实现者想简化，把 `tideflat.groups` 直接设成跟 `plains_river.groups` 去掉最后一条 `shipwreck` 完全相同也是可以的（我列的版本已经等价于这个简化）。
