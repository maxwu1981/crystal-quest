# HD-2D 这一轮改动的独立评估

评估日期 2026-09-07。**这份文档只做评估，没有改任何代码、没有改任何美术。**
被评估的是 `8cdc04e` → `c4daac1` → `67d4e7a` 三个提交（评估进行到一半时 `67d4e7a` 落地，
所以下文的「现在」= `67d4e7a`，「量化前」= `8cdc04e`，「只量化未吸附」= `c4daac1`）。

---

## 一句话结论

**素材已经够格了，画面之所以还看不出歧路旅人，缺的不是像素，是「光、影、镜头」三样，
而这一轮的力气主要花在了压色数上——那恰恰是唯一测不出观感变化的一项。**

具体说：这一轮七条里，**真正改变了观感的只有一条半**（MOOD 色调层，加上刚落地的透视地面）；
两次量化（第 4、5 条）合起来把颜色数字压掉了 7～10 倍，而边缘锐利度只动了 1.4%，
块感只走到目标的 12～18%。同时最要命的一件事没人碰：**导演最常看的那两张迷宫，
战斗根本没用上这一批新背景**——它们走的是 fallback，人还浮在天上。

# 一、逐条打分

| # | 改动 | 判定 | 一句话证据 |
|---|---|---|---|
| 1 | 十四张瓦片 / 四套背景 / 童乩改用 Gemini 美术 | **真起作用，但欠了两笔债没还** | 物件瓦片自带的地面与房间地板 ΔRGB 仍是 28～282，量化前后几乎没动 |
| 2 | 战斗背景只画地平线以上 | **方向对，实现反了** | 每幅画丢掉 58～65%，剩下的还放大 3.0～3.14×，角色像素密度是背景的 3.1 倍 |
| 3 | 两张迷宫补 MOOD 并提到 22% | **本轮最实在的一条** | 色相集中度 0.536 → 0.631（+18%）；第一版只有 +0.015，等于没做 |
| 4 | `posterize_luma` 量化瓦片 | **半分，且弄坏了一张** | 老瓦片 9～33 色，新瓦片压完仍 185～1107 色；石棺被压到 19 色、灰缝染蓝 |
| 5 | 吸附回母版调色板 | **半分，「数字变好看」的成分居多** | 色数 522→72（7×），但梯度 15.22→15.43（+1.4%），块感只走了 12～18% |
| 6 | 背景层单独开插值 | **起作用，但没解决根本问题** | 去掉了最近邻方块，可源图只有 512 宽对 1536 画布，它仍然是**低分辨率被平滑放大** |
| 7 | `perspRows` / `converge` 透视地面 | **已经接上了，而且几乎免费** | plains 1.09 ms/帧 vs 无透视的 fallback 1.02 ms；但 fallback 自己没接上 |

下面逐条给证据。

## ① Gemini 美术替换：真起作用，但两笔债一分没还

**起作用的部分**不用多说——十四张瓦片和四幅背景的内容质量比程序化那版高一个档次。

**第一笔债：每张物件瓦片仍然自带一层它自己的地面，量化完全没碰这件事。**
`docs/HD2D方案.md` 第一节把这条列为「最急」，量的是「瓦片底部 30% 的均色」与房间地板的 ΔRGB。
我用同一个量法比对量化前后（隘寮石城主地板 `flagstone` 均色 105,101,97）：

```
瓦片            量化前 ΔRGB   现在 ΔRGB    变化
altar               258          282      更不搭
pillar              185          170      好一点
plank               161          174      更不搭
carpet              130          151      更不搭
stove               131          115      好一点
idol                147          136      好一点
sarcophagus          94          107      更不搭
crate / rubble / seal_stone / ore_vein     基本没动
```

五张更不搭、四张好一点、四张没动，**而最大的两个离群值（altar 258、pillar 185）原地不动。**
量化和「自带地面」是两件正交的事，压色数不可能修好它。
方案文档把「重出图统一地面」排在阶段 0-2（当天见效的止血），**这一步被跳过了。**

**第二笔债：新旧两种画法并置的落差，只关上了一小半。**
色数不是好指标（连续调的图里大半是差 1～2 级的近似色），所以我改量**面积加权**：
「覆盖 90% 画面需要几种颜色」——这才决定「读起来平不平」。

```
老瓦片（在游戏里用的那份 96×96）
  flagstone 3 色   cave_floor 3 色   path 3 色   wall 4 色   floor 8 色

新瓦片        量化前 →  现在
  stone_wall    259 →   21      ✔ 已经跟老瓦片同一量级
  altar         868 →   58
  pillar       1022 →   79
  rubble       2909 →  178
  arch_door    2421 →  212
  carpet       1630 →  262
  throne       2453 →  284
  stove        2240 →  376
  ore_vein     2479 →  389
  crate        3749 →  454      ✘ 仍是老瓦片的 57～150 倍
```

压掉了 10～20 倍，是真的；但目标是 3～8 色，现在是 21～454 色。
**石墙、祭坛、廊柱三张已经到位，木箱、矿脉、灶台、王座四张还差两个数量级。**

## ② 战斗背景只画地平线以上：方向对，但「高分辨率背景」是反的

`src/battle/backdropDraw.js` 的 `plate()`（第 46 行）现在只取画的下缘一段：

```
bg_plains  母版 512×240  只用下缘 35%（84 行）→ 丢弃 156 行 = 65%
bg_cave    母版 512×240  只用下缘 38%          → 丢弃 62%
bg_deep    母版 512×240  只用下缘 42%          → 丢弃 58%
bg_shrine  母版 512×240  只用下缘 37%          → 丢弃 63%
```

**每一幅 Gemini 画的天空、太阳、云、山，六成以上直接扔掉了。**
而剩下的那一条还要**放大 3.0～3.14 倍**才铺满战场宽度（512 源像素 → 1608 画布像素）。

HD-2D 的核心对比是「细腻的场景 + 粗糙的角色」。现在这里的实际像素密度是：

```
背景   512 源像素 → 1608 画布像素   =  0.32 源像素 / 画布像素
角色    96 源像素 →   96 画布像素   =  1.00 源像素 / 画布像素
⇒ 角色的像素密度是背景的 3.1 倍。**对比是反的。**
```

在 `EVAL_batnat.png` 那张原始精度截图上一眼可见：顶上那条竹丛是软的、糊的，
前面站着的三个人是刀锋一样硬的。**这不是 HD-2D，是把背景当远景糊掉了。**

修法（按便宜排序）：把 `bg_*` 母版按实际用到的画幅重出（1608 宽 × 84 高那个比例），
或者干脆把地平线的画幅还给它——现在 116 逻辑像素的地面全是程序化的平面，
而那幅画只占 36 像素，**画得最好的东西占画面最小**。

## ③ MOOD 色调层：本轮唯一一条观感真的变了的改动

我把 `MOOD.fort_ailiao` 拆成三种状态各渲染一帧（同一机位、同一帧号），量全屏统计。
「色相集中度」= 用彩度加权的色相圆形集中度 R，越接近 1 表示全画面的色相越收在一起——
这正是「几种地板读不读得成一个空间」的直接读数。

```
                  平均明度   明度标准差   平均彩度   色相集中度
无色调层             99.8      36.1      26.6      0.536
第一版 #e8d6b0×0.20  96.5      35.0      28.2      0.551   ← +0.015，等于没做
现在 #c9a05c×0.34    86.6      31.7      32.0      0.631   ← +18%
```

**commit 里「第一版等于没上色」的自我判断完全正确，而改完这一版是真的起了作用。**
这是这一轮里唯一一条我能拿出「观感改变」证据的改动。

两点更正：

1. **实际压暗是 13%，不是 22%。** multiply + globalAlpha 的合成是
   `out = dst × (1 − a + a×src)`，按明度加权算 `#c9a05c × 0.34` 是 0.878，压暗 12.2%，
   实测 99.8 → 86.6 = 13.2%，对得上。commit 写的 22% 是只按 B 通道（最暗那个）算的。
2. **色调层治不了两种毛病，因为 multiply 是乘法、保比例。**
   - *治不了「路和墙一样亮」*：隘寮石城主地板 `flagstone` 明度 101.7，主墙 `stone_wall` 明度 90.1，
     **差 4.6%**。上完色调是 89.4 对 79.0，**差 4.1%——反而更小。**
     导演最早那句「分不清哪是路哪是背景」，在隘寮石城的根因就是这 4.6%，
     它没有被这一轮的任何一条碰到。（万金古塚是 26.4%，那张没问题。）
   - *治不了色相离群*：隘寮石城上完色调之后，13 种瓦片里 11 种落在色相 23°～70° 的暖带里，
     而 `grass` 在 **129°、彩度 114**，`tree` 在 **123°、彩度 75**，`water` 在 183°。
     一块尖叫的绿草坪长在一座暖褐色的石城里，乘法色调把它一起转了，转完还是离群。

## ④ `posterize_luma` 量化：半分，而且弄坏了一张

**做对的部分**：确实避开了 `posterize()` 三通道独立取整那个坑的大头，彩度基本没变
（altar 14.2→14.5、arch_door 11.1→10.8、stone_wall 10.6→9.9，全在噪声内）；
平坦度（相邻像素明度差 <1.5 的比例）从 15.6～64.1% 提到 50.5～78.3%，
跟老瓦片的 41～83% 已经同一量级。这两条是真的。

**做得不够的部分**：见 ① 的面积加权表——`posterize_tiles.py` 的文档串写着
「8 档压完落在 16～76 色，正好跟老瓦片的 48～305 同一量级」，
**这句话是在 128×128 母版上量的，而游戏用的是 96×96 派生图**，
128→96 是 0.75 倍的面积平均，会重新插出一堆过渡色。实际母版压完是 265～1927 色，
派生完是 185～1107 色，跟老瓦片的 9～33 色差 6～120 倍。

**做坏的部分（详见第三节）**：`tile_sarcophagus` 被压成 19 色；
石墙的蓝偏没有消失，只是变小了。

## ⑤ 吸附母版调色板：数字很漂亮，画面几乎没动

这是导演特意点名要查的一条，查下来**导演的怀疑是对的**。

**先说做对的两件事（都是真的）**：

```
                       吸附前 → 吸附后（65 张角色/怪物图的中位数）
色数                     522  →   72        7.3 倍
孤立噪点像素占比         29.5% →  17.2%     降 42%，65/65 张全部下降
```

「孤立噪点」= 颜色跟上下左右四个邻居全都不同的像素，是面积平均缩小最典型的产物。
降 42% 是实打实的清理。

**再说没做到的那件事——commit 和文档串里都写着「边缘重新利落」，这句话数据不支持**：

```
                         吸附前 → 吸附后      方案文档自己那条「缩 1/3 再最近邻放大」能到
明度梯度（锐利度）       15.22  →  15.43       —          （+1.4%，噪声内）
横向同色连段（块感）
  char_boxer_down         1.82  →   2.11      4.93
  char_tangki_down        1.57  →   1.81      4.27
  char_general_down       1.61  →   1.83      3.90
  enemy_goblin            1.69  →   2.37      4.65
2×2 纯色块占比
  char_tangki_down        16.3% →  20.9%     57.9%
  char_general_down       19.7% →  24.0%     57.1%
  enemy_ghost              4.7% →   8.2%     51.7%
```

**只走了应走路程的 12～18%。**
原因很清楚：`snap_to_palette` 把每个像素映射到调色板里**最近**的一色，
而母版调色板有 48～88 色，密到「肤色和头发的 50/50 混色」几乎总能找到一个很近的落点——
于是那条模糊的过渡带原样留着，只是换了个名字。色数掉下来了，**空间上的软没有变硬。**

**丢了什么**：几乎什么都没丢。整体 RMS 只有 6.24/255 = 2.4%，单像素最大 ΔRGB 37（满值 441）。
我把三个角色的脸放大 5 倍逐像素比对（拳头师 / 童乩 / 将军的眼睛、发际线、头巾），
**看不出可指认的细节损失**——但也看不出边缘变利落。这一步既没弄坏，也没真的改善。

> 结论：这一条**该做**（清掉 42% 噪点是有价值的），但它**不是**「角色变块」，
> 而 HD-2D 要的正是「角色变块」。方案文档阶段 1-2 写的那条路
> （母版缩到 32×48 → 量化 → 最近邻放大回 96×144）才是目标，现在离目标还有 82～88%。

---

## ⑥ 背景层单独开插值：起作用，但没解决根本问题

`plate()` 里 `imageSmoothingEnabled = true`（第 57 行）确实去掉了最近邻的 3×3 方块边，
而且在离开前还回 `false`（第 61 行），没有污染后面的精灵绘制——这一处写得对。

但见 ②：源图只有 512 宽，放大 3.14 倍。**开插值把「方块边」换成了「糊」，
两头短处去掉了一头，剩下的那头还在。** 真正的解法是把母版画到用得上的分辨率。

---

## ⑦ `perspRows` / `converge`：已经接上了，成本几乎为零

导演说「这一步还没接上」——评估期间 `67d4e7a` 落地，**已经接上了**，
四套画好的背景（plains / cave / deep / shrine）全都在用，地平线从 100/112/120/104
抬到了 36/40/44/38，队伍 y=44..122 和敌人 62..132 因此全部落到地平线**以下**。

性能实测（同一台机器，`paintScene` 单独计时 300 帧，全程不读像素）：

```
plains  1.092 ms/帧   （有整幅画 + 13 条 converge 线）
cave    0.748 ms
deep    0.655 ms
shrine  0.717 ms
default 1.021 ms      （没有画、没有透视地面）
```

**透视地面比没有透视地面只贵 0.07 ms。** 这一条做得干净。

**但它没接在 fallback 上，而 fallback 正是导演最常看的两张图在用的——见第二节第一条。**

# 二、跟歧路旅人的差距，按最刺眼排序

## 第一刺眼：隘寮石城和万金古塚的战斗，根本没用上这一批新背景

这不是审美问题，是接线漏了。`src/battle/backdrop.js` 第 19–20 行：

```js
const ZONE_BG = { village_field: 'plains', plains: 'plains', cave: 'cave', cave_deep: 'deep' };
const MAP_BG  = { village: 'plains', overworld: 'plains', cave_1: 'cave', cave_2: 'deep', cave_3: 'shrine' };
```

而 `data/maps/fort_ailiao.json` 的 `encounterZone` 是 **`fort`**，
`data/maps/tomb_wanjin.json` 是 **`tomb`**——两个都不在表里，
两张地图也都不在 `MAP_BG` 里。于是 `kind` 落到 `'default'`，走 `drawFallback()`。

我在浏览器里从隘寮石城触发了一次真遇敌，回读 `scene.backdrop` 得到 `{kind:"default"}`，
截图确认：**天是一条渐变，没有那幅画；地面从 `PANEL_Y - 40 = 112` 起，
没有 `perspRows`、没有 `converge`；队伍在 y=44/70/96/122、敌人在 62/82/114/132，
最上面三个人和两只怪整个浮在天上。**

`67d4e7a` 的标题是「战斗地面改成透视斜面：角色不再浮在地平线上方」——
在导演天天看的那两张地图上，**他们还浮着**。十二张地图里只有五张（village / overworld /
cave_1 / cave_2 / cave_3）能看到这一轮的战斗背景成果。

**最便宜的改法**：`ZONE_BG` 加两行——`fort: 'shrine'`（石城夜战，立石那套色温最近）、
`tomb: 'deep'`。零风险、零新美术、一分钟。如果要正式的，再各出一幅画，
但那是之后的事，**现在这两行的价值远大于这一轮做过的任何一次量化。**

## 第二刺眼：战斗画面里没有一片落影，一个人也没有

项目自己已经知道这条规矩。`src/field/npc.js` 第 37 行有现成的 `drawShadow()`，
第 90 行的注释一字不改地写着：

> `drawShadow(ctx, dx, dy);   // 树和宝箱都有落影，人没有的话看着像浮在地上`

地图上主角有（`src/field/FieldScene.js:330`）、NPC 有、树有、宝箱有。
**`src/battle/` 二十六个文件里，`drawShadow` 出现 0 次。**
（`ellipse` 有十几处，全是法术特效的光环，没有一处是接地影。）

加了透视斜面之后这条更要命：地面在说「这是一块往后退的地」，
四个人踩在上面**不留一点接触痕迹**。歧路旅人的角色脚下永远有一团被光压出来的软影，
那是「站在场景里」和「贴在场景上」唯一的区别。

**最便宜的改法**：`src/battle/render.js` 画每个 actor 之前调一次现成的 `drawShadow`，
椭圆宽度按 `artW(spr)` 走。不用新文件、不用新美术。

## 第三刺眼：地面在说透视，角色在说贴纸

`src/battle/hudBits.js` 第 6–7 行：

```js
export const ENEMY_CENTERS = [[48, 62], [100, 82], [48, 114], [100, 132]];
export const PARTY_X = 204, PARTY_Y0 = 44, PARTY_DY = 26;
```

队伍固定在 x=204，y = 44 / 70 / 96 / 122。可见地面是 y=36（地平线）到 152（面板），
**四个人跨了这块地纵深的 64%，而四个人一样大。**

`converge()` 已经把灭点画出来了（`EVAL_batnat.png` 里那些朝中心收拢的畦沟一眼就看得见），
**灭点一旦画出来，尺寸不跟着走就是自相矛盾**——地面在说「上面那个人站得远」，
角色在说「我们四个一样近」。在原始精度截图上，这是四个人里最先被眼睛抓到的错。

顺带说：`perspRows` 那几条横向的浅色带（平原 4 条 `#e4ce96` 的田埂）
在这块空地上读起来像运动场的跑道线，不像田埂——因为它们两侧没有任何东西证明那是田。

**最便宜的两条改法（选一）**：
- 按深度缩放：`k = 0.82 + 0.18 × (y − hz) / (bottom − hz)`，最远 0.82 倍、最近 1.0 倍。
  一行，布局不动，四个人立刻站进那块地里。
- 或者把队伍从竖排改成横向扇开（歧路旅人就是横排，所以它同样大是对的）——
  但这会动 `ENEMY_CENTERS` / `PARTY_X` 和一串 UI 坐标，比上一条贵得多。

## （第四刺眼，附带提一句）草和树在石城里尖叫

见第一节 ③ 的色相表：隘寮石城上完色调之后 13 种瓦片里 11 种落在 23°～70°，
`grass` 在 129°/彩度 114、`tree` 在 123°/彩度 75。**全屏最高的两个彩度，
色相离所有人 60～100°。** 这两张是最老的程序化瓦片，颜色是当年按「村外草地」调的。
最便宜：给这两张单独降一档饱和度（离线改 PNG，不动代码），或者给 MOOD 加一个
`desat` 字段走一次 `globalCompositeOperation='saturation'`。

# 三、做坏了的地方

## 1（真的坏了）`tile_sarcophagus` 被量化压死，灰缝染成蓝色

```
                  量化前 → 只量化 → 现在
色数                1619  →   110  →    19
覆盖 90% 面积需要    698 色 →       →     5 色
文件大小           12272 B →  3301 →  2101 B
蓝偏像素(B−R>15)     0.4% →  16.9% →  12.1%
```

**明度直方图说清了发生了什么**（按 16 一档）：

```
量化前   16:8%  32:6%  48:9%  64:29%  80:35%  144:1%  192:6%
现在      0:6%  32:6%  48:41%         96:36%  144:1%  192:7%
```

原图整块地板的色调集中在**相邻的 64 和 80 两档**（合起来 64% 的面积，层次差 16）。
`posterize_luma(levels=8)` 的档距是 255/7 = **36.4**，这块地板正好骑在一条档界上，
于是被**劈成 48 和 96 两半——原本 16 的层次变成 48 的断层**。

放大 6 倍看（左：量化前 / 中：现在 / 右：把 B−R>15 的像素标红）——
**石头本身的青灰色被抽干成中性灰，而砖缝和裂纹变成了蓝绿色的虚线**，
标红的像素精确地描出所有灰缝。原来是一块青灰石，现在是灰石头 + 蓝缝。

**根因**：`posterize_luma` 用的是全局固定 8 档。
**对整幅动态范围大的画有效，对整块色调只跨一档多的低反差瓦片会把它劈开。**
`tools/posterize_tiles.py` 的 `KEEP = 400` 那道闸只挡「色数已经够少」的，
挡不住「色数很多但明度跨度很窄」的——石棺量化前 1619 色，轻松过闸。

## 2（真的坏了，只是没上次严重）蓝偏没有消失，只是从「整面墙」变成了「灰缝」

`c4daac1` 的 commit 写着「实测石墙 933→265 色而彩度 11.6→10.9，**蓝色偏消失**」。
逐像素量下来这句话不成立：

```
蓝偏像素占比（B − R > 15）    量化前 → 只量化 → 现在
tile_stone_wall               0.0%  →   3.7% →   3.9%    ← commit 点名说修好的那张
tile_sarcophagus              0.4%  →  16.9% →  12.1%
tile_throne                   0.4%  →   1.1% →   3.7%    ← 这一张是**吸附**那一步加的
```

**机制不是 255 截断**（我在四张母版上直接算过，被截断的像素 0.0%），
而是**乘法本身放大彩度**：`posterize_luma` 走的是
`k = 目标明度 / 原明度`，然后 `r,g,b` 同乘 k。
比例是保住了，但**彩度 max−min 也跟着乘了 k**——一个略带冷调的近灰石头被提亮一档，
它那点冷调就被放大一档。实测被放大彩度的像素占比：
stone_wall 15.3%、throne 20.4%、seal_stone 24.4%、sarcophagus 48.7%；
单像素 B−R 最大增量 throne **+45**。

暗部反过来（k<1 会压掉彩度），所以整体平均彩度看不出变化（11.6→10.9 是真的）——
**平均值掩盖了「亮部更艳、暗部更灰」这个分布变化**，而人眼看的正是这个。

修法（不在我职权内，只是记下）：`posterize_luma` 改成在 **HSL 的 L 上**取整
（或取整后把 max−min 按 1/k 还原回去），而不是整条 RGB 同乘。

## 3（说法不准，不算坏）「压暗 22%」实际是 13%

见第一节 ③。数值本身选得好（观感是对的），只是文档里的百分比是按单通道算的。

## 4（**没坏**）装备叠加层完全对得上，而且对比反而更好

导演担心的两件事我都查了：

**（a）落点会不会歪——不会，剪影分毫未动。**
49 张 `char_*.png` 的 **alpha 通道逐像素比对，0 张有任何变化**。
`derive()` 里 `threshold_alpha` 在 `snap_to_palette` 之前跑，而吸附只改 RGB。
`src/assets/equip.js` 的叠加层是按 16×24 逻辑坐标画在物理像素空间的
（`R()` / `RL()`，见文件第 50–65 行的注释），跟角色的颜色毫无关系，剪影不变就一定还对得上。

**（b）颜色会不会糊在一起——不会，反而更清楚。**
量「`MAT` 里每种材质色到该角色身上最近一色的距离」（越小越容易糊进身体）：

```
                    吸附前中位 → 吸附后中位     最险的一对
char_boxer_down        11.5   →   18.7        iron #3a3f45   4 → 9
char_tangki_down       10.5   →   21.2        wood #8d6a43   8 → 8
char_general_down      12.8   →   21.3        wood #8d6a43   8 → 8
char_talisman_down     17.2   →   22.7        wood #8d6a43   8 → 8
```

**距离全线上升**——因为身上那些「介于两色之间」的过渡色正是被吸附掉的那批，
它们消失之后装备反而更跳出来。最险的一对是木质握柄 `#8d6a43` 对皮肤/皮革色，
距离 8，但**吸附前也是 8**，不是这次改动造成的。

我还在浏览器里把 `bronze_sword_down` / `iron_armor_down` / `silk_robe_down`
三层实际叠到 `boxer_down` 上渲染出来看过：剑、肩甲、腰带三样都读得清清楚楚。

## 5（**没坏**）手机横屏不会裁掉背景的任何部分

`src/core/Game.js` 的 `fitCanvas()` 用 `Math.min(innerWidth/W, (innerHeight−pad)/H)` 等比缩放，
**只改 CSS 尺寸，画布逻辑分辨率恒为 256×224**，所以整幅永远在画面内，多出来的是左右黑边：

```
                    CSS 尺寸      左右黑边合计
iPhone 13 横屏      446 × 390        398 px
iPhone 15 PM 横屏   491 × 430        441 px
Android 2340 横屏   411 × 360        369 px
iPad Pro 11 横屏    953 × 834        241 px
```

**真正的裁切不在手机上，在 `plate()` 里**——每幅画被丢掉 58～65%（见 ②）。
另外附带一句：iPhone 13 横屏是 446 CSS × DPR 2 = 892 设备像素显示 1536 的画布，
**角色被下采样到 0.58 倍，而背景是从 512 上采样到 892（1.74 倍）**——
在手机上「细腻背景 / 粗糙角色」的对比比桌面上还要更反一点。

## 6（**没坏**）十四张瓦片里其余十三张没有糊掉，测试和性能也没事

- 除石棺外，其余十三张的明度被推动 >24 的像素**最多 4.7%**（arch_door），
  放大 3 倍逐张目视比对，没有第二张出现可指认的糊或断层。
- 梯度（锐利度）大多**微升**（crate 21.3→24.1、rubble 25.7→28.2），方向是对的；
  只有 `plank` 下降（11.9→10.8）且平坦度从 55% 冲到 73.6%，是十四张里第二危险的一张，
  但目视还没到坏掉的程度。
- 我一度怀疑 `tile_plank` 上下移了位，逐行明度做了对齐搜索，**最佳偏移 = 0，没有移位**。
- 母版里**没有一个半透明像素**（char / enemy / tile 各抽查，semi = 0），
  所以 `palette_of(cut=8)` 不会把边缘的脏色混进调色板——这一处是干净的。
- `tests/index.html` 跑完 **71/71 通过**。
- `paintScene` 0.655～1.092 ms/帧，透视地面只比不带它的 fallback 贵 0.07 ms。
